## 1. 1분 요약

이 프로젝트는 **AI에게 일을 시키는 프롬프트 모음이 아니라, AI 작업의 입력·권한·상태·결과·검증·재시도를 일반 프로그램으로 관리하는 로컬 실행 제어기**를 만드는 작업이다.

출발점은 여러 AI 세션을 사용할 때 사람이 작업을 나누고 결과를 복사·중계하며, 실패한 실행을 추적하고 다시 이어야 하는 부담이었다. 목표는 프로젝트마다 자동화 코드를 새로 만드는 대신, 공통 실행 코어와 프로젝트별 설정을 분리하여 재사용하는 것이다.

현재 핵심 구현인 B1은 Python 기반 순차 오케스트레이터다. 한 번에 하나의 Worker 세션을 실행하고, SQLite 원장에 진행 상태를 기록하며, 구조화된 결과와 실제 파일·검사 결과를 확인해 다음 작업 진행 여부를 결정한다. 프로젝트별 규칙은 Project Pack으로 분리한다. 실제 모델 연결은 고정 버전의 Codex SDK 어댑터가 담당한다.

이를 평가하기 위해 별도의 Benchmark Runner도 구현했다. 동일한 과제를 여러 실행 방식으로 수행하고, 독립 검사기와 측정 기록을 이용해 비교한다. 개발 과정에서는 비교 지표의 편향, 숨은 채점표의 오판, SDK 설정 변화와 실패 분류 문제를 발견하고 검증 방식을 보완했다.

중요한 경계는 다음과 같다.

- 구현된 제품은 **순차 실행기**다. 여러 AI가 동시에 협업하는 병렬 제품이 완성된 것은 아니다.
- 실제 모델 연결과 다단계 작업 수행 기록은 있다. 그러나 범용 생산성 향상·비용 절감·현업 도입 효과가 확정된 것은 아니다.
- 자동검사와 복구 기능이 존재한다는 사실과, 모든 경계에서 그 기능이 정확하다는 주장은 다르다. 9월 8일 감사 당시 발견은 14건이며, 이후 안내·연구 인용의 문서 정정을 제품 코드 결함 해결로 세지 않는다.
- 지원자의 확인 가능한 역할은 문제 정의, 범위와 제약 설정, AI 기반 개발 진행, 검증 방법에 대한 문제 제기, 검토 요청과 설계 승인이다. 코드·시험·문서 작성에는 Codex 등 AI의 기여가 크다.

## 2. 배경과 해결하려던 문제

### 2.1 사용 상황

Git으로 관리되는 코드·문서 프로젝트에서 AI 세션을 반복적으로 사용하는 개인 개발자가 주된 사용 대상이다. 특정 회사의 제조 공정이나 고객 업무를 대상으로 이미 구축·납품한 시스템은 아니다.

초기 설계는 이전의 별도 다중 세션 실험에서 얻은 경험도 참고했다. 그 경험에는 중앙 AI 조정 비용, 완료 신호와 실제 종료의 불일치, 상태 정보 비대화 등이 있었다. 다만 그 선행 프로젝트의 성과 수치와 현재 저장소의 성과를 합쳐서는 안 된다. [S1]

### 2.2 문제를 시스템 요구사항으로 바꾼 방식

| 문제 | 대응 설계 |
|---|---|
| 사람이 세션 사이에 작업과 결과를 전달해야 함 | 명시적인 Task 계약과 산출물 참조를 통해 프로그램이 전달 |
| AI가 완료했다고 말해도 결과가 틀릴 수 있음 | 모델의 완료 보고와 실제 완료 판정을 분리하고 자동검사 수행 |
| 중단 후 어디서부터 이어야 할지 불명확함 | Run·Task·Attempt·Session 상태를 SQLite 원장에 기록 |
| 오래된 입력이나 허용 범위 밖 파일 변경이 섞임 | 입력 해시·신선도·읽기/쓰기 범위 검증 경계 구성 |
| 다른 프로젝트에 적용할 때 코어까지 복사·수정하게 됨 | 버전이 있는 공통 코어와 Project Pack 분리 |
| 여러 세션을 사용했다는 이유만으로 효율적이라고 판단함 | 직접 실행 기준선과 비교하고 품질·시간·사용량·사람 개입을 구분 |

이 표는 대응 설계와 구현 방향을 설명한다. 모든 방어 기능이 완전하게 검증됐다는 뜻은 아니며, 현재 알려진 빈틈은 9절에 별도로 정리했다.

## 3. 전체 구성: 제품과 평가 도구를 구분해서 이해하기

```text
외부 작업 프로젝트
  ├─ Project Pack: 프로젝트 설정·정책·검사 규칙
  └─ Run Spec: 작업 목록·의존성·입력·범위·완료 조건
          ↓
B1 순차 오케스트레이터
  ├─ 계약 검증 / 순차 스케줄러
  ├─ SQLite 실행 원장 / 산출물 저장 / 복구 / 보고
  └─ Runtime 어댑터 → Codex SDK 또는 FakeRuntime
          ↓
Worker 결과 + 실제 파일 → 자동검사 → 완료 / 재시도 / 중단 판단

별도 평가 계층: Benchmark Runner
  실행계획 → 동일 과제의 기준선/B1 실행 → 독립 Judge → 측정·봉인·비교

개발 지원 계층
  오류·해결 기록 도구 + 설계·심사·실험·운영 문서
```

### 3.1 B1: 범용 제품의 핵심

- Project Pack과 Run Spec을 읽고 실행 계약을 검증한다.
- 한 번에 하나의 Worker 세션만 실행한다. 일반 코드는 상태 전이와 다음 Task의 실행 여부를 관리한다.
- 모델 응답을 구조화된 결과로 받아 실제 종료 상태, 산출물, 변경 범위, 입력 신선도, Check 결과를 검사하는 경계를 둔다.
- 재시도, 중단 후 상태 조정, controller lock, 백업 및 보고 기능을 제공한다.
- CLI 이름은 `lao`다. 프로젝트 초기화, 실행계획 검증, 시작·재개·조회·취소, 보고, Schema 내보내기, 복구·백업 관련 명령이 있다. [S2][S3]

### 3.2 Project Pack: 재사용을 위한 프로젝트별 구성

프로젝트 식별·capability·정책·Check를 담는 네 YAML 구성을 공통 코어와 분리한다. 외부 프로젝트가 코어 버전을 고정하고 프로젝트별 규칙을 제공하는 방식이다. 전체 소스를 프로젝트마다 fork하는 방식은 기본 경로가 아니라 예외적 선택지로 설계했다. [S1][S2]

이 구조를 구현한 것과, 여러 실제 외부 프로젝트에서 코어 수정 없이 재사용 효과를 입증한 것은 별개다. 후자의 채택 조건은 아직 충분히 입증되지 않았다.

### 3.3 Runtime 어댑터: 모델 실행과 제어 로직의 분리

공통 실행 경계 뒤에 FakeRuntime과 CodexRuntime을 둔다. FakeRuntime은 실제 모델을 호출하지 않고 성공·실패·중단 같은 조건을 재현하는 데 사용한다. 실제 연결은 프로젝트에서 고정한 Codex SDK를 사용한다. 따라서 모든 회귀시험에 유료 모델 실행이 필요한 구조는 아니다. 다른 모델 제공자까지 실제 연동을 완료했다는 뜻은 아니다. [S3]

### 3.4 Benchmark Runner: 오케스트레이터의 효과를 검증하는 별도 도구

평가용 과제, 실행 순서, 환경·권한, 독립 Judge, Measurement와 Evidence를 관리한다. 일반 B1 비교 어댑터는 CLI와 공개 Schema를 경계로 사용한다. 후속 SDK 통제 비교와 Phase F 경로는 일부 공통 계약·Worker 코드를 재사용하므로, 모든 평가 경로가 제품 내부 코드와 완전히 분리돼 있다고 표현하면 안 된다. [S4][S13]

`lao-bench` CLI와 실험별 드라이버가 있으며, 제품의 작업 원장과 평가용 Cell·봉인 상태는 서로 다른 계층이다. 실행 기록의 해시와 출처를 검증하는 기능은 결과가 바뀌지 않았음을 확인하기 위한 것이지, 정답 판정 자체의 타당성을 보장하는 기능은 아니다.

### 3.5 개발 오류·해결 기록 도구

구축 중 발생한 문제를 JSON 정본으로 기록하고 Markdown 인덱스를 생성한다. 원인, 대안, 해결, 회귀시험, 근거를 남기는 용도다. `new`, `resolve`, `validate`, `render`, `check` 기능이 있다. 실제 Worker 실행 상태를 저장하는 SQLite 원장과 혼동하지 않는다. [S12]

## 4. 핵심 개념과 실행 흐름

| 용어 | 이 프로젝트에서의 의미 |
|---|---|
| Run | 사용자가 요청한 하나의 전체 실행 |
| Task | 목표·입력·범위·의존성·완료 조건이 정해진 작업 단위 |
| Attempt | 특정 Task를 수행하려는 한 번의 시도 |
| Session / Thread | Worker 모델의 실행 대화 단위. Task마다 새 세션을 사용하는 경로가 있음 |
| Artifact | 경로·해시 등으로 식별하고 보존하는 결과물 또는 근거 |
| Check | 작업 계약에 따라 실제 결과를 검사하는 자동검사 |
| Judge | 평가 계층에서 결과를 판정하는 별도 검사기. 이름만으로 LLM 심사자를 뜻하지 않음 |
| Cell | 고정된 실험계획 안에서 특정 실행 방식을 시험하는 단위 |
| Candidate / Plan / Seal | 실행 대상의 고정된 소스·구성, 실행계획, 그 정체성과 결과를 연결하는 무결성 기록 |

일반적인 B1 흐름은 다음과 같다.

1. 프로젝트 설정과 Run Spec을 검증하고 실행 원장에 기준 정보를 결합한다.
2. 의존성과 현재 상태를 바탕으로 실행 가능한 Task 하나를 선택한다.
3. 입력·허용 범위·완료 조건을 담은 계약을 Runtime 어댑터에 전달한다.
4. Worker의 종료와 구조화된 결과를 수집한다.
5. 실제 파일과 Artifact, 변경 범위, 신선도, Check 결과를 검사한다.
6. 결과를 원장에 반영하고 다음 Task, 허용된 재시도, 중단 중 하나를 결정한다.
7. 중단·재개 시 기록과 실물을 대조하고, 보존된 실행 근거로 보고서를 제공한다.

여기서 중요한 설계 원칙은 **확률적인 생성은 AI가, 권한·상태·완료 조건의 집행은 결정론적 코드가 담당한다**는 것이다. 단, 현재 구현의 복구·입력·취소 경계에는 감사에서 발견된 미해결 문제가 있다.

## 5. 기술 스택과 주요 설계 판단

| 기술·구조 | 실제 사용 목적 | 설명할 때의 경계 |
|---|---|---|
| Python 3.12, src-layout 패키지 | 실행기·평가 도구·CLI 구현 | 두 패키지는 Python `>=3.12,<3.13` 선언 |
| Pydantic v2, JSON Schema, PyYAML | 타입 계약, 외부 결과 검증, 프로젝트 설정 | 저장된 공개 Schema 일부의 동기화 결함이 후속 감사에서 발견됨 |
| SQLite, 트랜잭션, controller lock | 실행 상태 정본과 동시 변경 통제 | DB를 사용한다는 사실만으로 모든 중단·복구가 안전한 것은 아님 |
| Git, SHA-256, 원자적 파일 저장 | 소스·산출물·실험 대상 식별 및 무결성 추적 | 파일 무결성과 의미적 정답은 다름 |
| RuntimePort / FakeRuntime / CodexRuntime | 모델 호출과 제어 로직 분리, model-free 시험 | 다수 AI 제공자 지원 완료로 확대하지 않음 |
| 프로젝트 고정 `openai-codex==0.144.4` | 실제 Codex 세션 연결 | 프로젝트 당시 고정 버전이며 최신 SDK라는 뜻이 아님 |
| pytest, 단위·계약·통합·실패 주입 시험 | 정상 경로와 오류·중단 경계 검증 | 일부 시험 통과와 전체 회귀 통과를 구별 |
| Windows 로컬 환경, Docker Judge | 실제 호스트에서 실행 및 격리된 평가 | Docker는 주로 평가 환경이며 모든 Worker가 컨테이너 안에서 실행되는 것은 아님 |
| Hatchling / wheel | 코어와 평가 도구 패키징, 설정·Schema 포함 배포 | 패키지 생성은 상용 배포 실적을 의미하지 않음 |

선택의 핵심은 기술의 종류보다 책임 분리에 있다. 중앙 AI 관리자에게 상태 판단까지 맡기지 않고, 작은 순차 실행기부터 만들어 기본 방식과 비교한 뒤 복잡도를 늘리는 방향을 택했다. B1은 병렬 Worker, 전용 Reviewer, 자동 Task 분해, UI, worktree 관리, 다중 호스트 controller를 구현 범위에서 제외했다. [S1][S2][S3][S5]

## 7. 대표적인 문제 해결 사례

### 사례 A. “여러 세션을 쓰면 좋아지는가?”를 검증 가능한 질문으로 바꾸기

- 문제: 수동 B0와 자동 B1의 비교에 사람의 대기시간과 서로 다른 실행 방식이 섞일 수 있었다. 일부 수동 중계 지표는 구현 구조만으로 유불리가 정해지는 문제가 지적됐다.
- 지원자의 확인 가능한 관여: 8월 6일, 두 방식에 사람 중계가 실제로 어떻게 들어가는지 질문하고 시험 방법과 대안의 재검토를 요청했다. 8월 7일에는 유용한지 아닌지를 신뢰할 수 있게 입증해야 한다는 요구를 제시했다.
- 프로젝트 차원의 대응: 같은 SDK·모델·과제·권한·Judge 아래 실행 구조를 단계별로 비교하는 C0/C1/C2/B1 설계를 만들었다.
- 구조: C0는 한 thread·한 turn의 통합 요청, C1은 같은 thread에서 Task별 turn, C2는 Task별 새 thread와 최소 중계, B1은 C2 형태에 원장·검증·재시도·복구를 추가한다.
- 확인 결과: 4-Cell pilot은 실제 연결을 확인했다. C0/C1은 탐색용이고 C2/B1은 방향성 판단용이다. 이 SDK 실험은 원래 목표인 사람의 운영 부담 감소를 직접 입증하지 않는다.
- 학습 포인트: 자동화의 효과를 주장하려면 실행 도구 차이와 사람 개입 같은 혼입 요인을 먼저 분리해야 한다. [S6][S7][S8][S9][S14]

### 사례 B. “검사를 통과했는가?”뿐 아니라 “검사가 올바른가?” 확인하기

- 문제: 9월 4일 B1은 R01~R13을 완료하고 누적 public Check 104회가 모두 통과했지만, hidden Judge는 13개 항목 중 2개를 실패로 판정했다.
- 원인: R-P11은 정상 동작보다 특정 소스 문자열의 존재를 요구했고, R-P13은 공개 계약상 가능한 표현을 허용하지 않고 비공개 정답 JSON과 완전히 같아야 통과시켰다.
- 기존 사전검증의 빈틈: 기준 정답과 준비한 오답을 구분하는 시험은 있었지만, 공개 계약을 만족하는 다른 정상 구현까지 인정하는지는 충분히 검사하지 않았다.
- 대응과 결론: 이 pair를 `DIAGNOSTIC_ONLY_NO_ROUTE`로 남겼다. 원래 결과를 고쳐 성공으로 재분류하거나, B1 채택의 공식 근거로 사용하지 않았다. 후속 qualification에는 정상 대안 사례를 포함하는 보완이 기록돼 있다.
- 학습 포인트: AI 솔루션에서는 출력물뿐 아니라 평가 기준의 의미적 타당성도 검증 대상이다. 정답 한 가지와 일치하는지보다 계약을 만족하는지를 봐야 한다. [S10][S13]

### 사례 C. 정상적인 SDK 상태 변화와 위험한 설정 변경 구분하기

- 문제: 후속 v25 실행에서 첫 B1 Task는 성공했지만 다음 세션 배차가 설정 검증 오류로 중단됐다.
- 원인: 검증된 첫 thread 시작 뒤 현재 workspace에 대한 trust 항목이 추가되면서 설정 해시가 달라질 수 있었다. 최초 preflight와 다음 세션 사이의 이 변화를 사전시험에서 연결하지 못했다.
- 수정: 자신의 검증된 thread 시작 이후, 정확한 현재 workspace에 새 trust 항목 한 개가 추가되고 연결된 origin·version만 바뀌는 제한된 전이를 허용했다. 나머지 설정·권한·경로·SDK 정체성은 기존과 일치해야 한다. 개인 설정 파일을 어댑터가 직접 편집하지 않도록 유지했다.
- 추가 수정: `dispatch_uncertain`을 환경 측 배차 실패로 보존하고, 제품 검사 실패와 섞이면 혼합 실패로 분류하여 정식 비교에서 제외하도록 했다.
- 검증과 한계: 집중·관련 회귀와 실제 CLI의 config-only 시험을 수행했다. 전체 benchmark-runner 시험에는 기존 개행 관련 실패 2건이 남았다. 수정 후 실제 모델을 사용하는 새 종단간 실행을 완료한 것은 아니다.
- 학습 포인트: 무조건 모든 변화를 허용하거나 차단하기보다, 허용되는 상태 전이의 정확한 조건을 계약과 시험으로 표현해야 한다. 환경 오류가 모델·제품 품질 평가를 오염시키지 않게 분류 경계를 유지해야 한다. [S11]

### 사례 D. 기능 존재와 기능 신뢰성을 분리한 전체 감사

- 문제: 과거의 실행 성공·봉인 통과·부분 회귀만으로 범용 실행기의 신뢰성을 설명하기 어려웠다.
- 수행: 제품의 공개 명령·계약·설정·원장·복구, 패키징, 비교 실행기, 개발 기록과 문서를 함께 점검하고 경계 조건의 반례를 확인했다.
- 확인: 완료 검사 재사용, 입력 참조, 실행 profile, 취소·백업, 공개 Schema, 평가 의미 등의 미해결 사항 14건을 분리했다.
- 상태: 감사와 최소 수정 계획은 완료했지만, 이 14건을 모두 수정한 것은 아니다. 안내 시점·인용 표본의 문서 정정은 후속 반영했으나 제품·평가 코드 수정은 이번 범위가 아니다. 9월 8일의 특정 trust·분류 수정과 후속 전체 감사의 발견을 혼동하지 않는다.
- 학습 포인트: 성공 사례뿐 아니라 어떤 조건에서 결과를 신뢰할 수 없는지를 명시하는 것이 자동화 도구의 품질 관리에 필요하다. [S13]

## 9. 현재 한계와 미구현 범위

### 9.1 후속 감사에서 확인된 주요 미해결 사항

제품 측에서는 과거 Check 결과 재사용 때문에 변경된 잘못된 산출물을 완료로 처리할 가능성, Task별 실행 profile·sandbox 요구와 실제 적용의 불일치, 누락되거나 잘못된 해시의 입력 참조를 충분히 거부하지 못하는 경계가 확인됐다. 활성 controller lock 때문에 취소 명령이 막히는 문제, 추적 파일 삭제 시 예외 처리, 불완전한 백업을 통과시키는 검증, 공개 Schema 두 종류의 동기화 불일치도 있다.

평가 도구 측에서는 재개 시 Session 식별자 충돌, 일부 구조화된 실패 정보의 유실, 실행 준비 후 deadline 재검사 공백, Profile I 개행에 따른 바이트 재현성 및 미구현 결과를 통과시킬 수 있는 의미 판정 문제가 확인됐다. 일부 연구 수치의 표본 해석과 안내 문서의 시점 불일치도 포함된다. [S13]

이 사항들은 모두 같은 종류의 실패는 아니다. 제품 기능 정확성, 평가 타당성, 기록·안내의 정확성을 나누어 이해해야 한다. 9월 16일에는 안내의 현재성·연구 표본 해석을 정정했지만, 제품·평가 코드의 결함을 새로 수정한 것은 아니며 전체 수정 완료 증거도 없다.

### 9.2 설계상 제외했거나 아직 입증하지 않은 것

- B2 병렬 Worker, B3 Reviewer, AI 자동 작업 분해·동적 계획, 사용자 UI, 다중 호스트 controller는 B1 구현 완료 범위가 아니다.
- 다른 실제 외부 프로젝트에서 코어 변경 없이 Project Pack만 교체하는 범용 채택 조건은 충분히 입증되지 않았다.
- 사람의 운영·복구 부담 감소, 비용 대비 효용, 장기간 안정성, 통계적 성능 우위는 확정되지 않았다.
- 모델 학습·파인튜닝, RAG, 컴퓨터 비전, 제조 불량 탐지·예지보전, MES/ERP 연동을 구현했다는 근거는 없다.
- 상용 서비스 출시, 현업 배포, 고객 수, 매출·비용 절감액, SLA 달성 실적으로 표현할 근거는 없다.

## 10. 지원자 역할과 AI 기여의 구분

### 10.1 기록으로 확인되는 지원자 역할

- 문제와 방향 설정: 프로젝트 종속 구현이 아니라 범용 도구를 먼저 만들고 실제 프로젝트와 분리하라는 요구를 제시했다.
- 설계 의사결정: 교차 검토 결과를 반영하고 다시 확인한 뒤 설계를 동결하도록 승인했다.
- 검증 방법에 대한 비판적 질문: B0/B1 비교에서 사람 중계가 실제로 무엇을 측정하는지 질문하고 대안 검토를 요청했다.
- 효용 검증 요구: 단순 구축 완료가 아니라 도구가 유용한지 아닌지를 믿을 수 있는 방식으로 확인하도록 요구했다.
- 개발 과정 관리: 구축 중 오류와 해결 과정을 별도 기록하도록 요청하고, AI에게 구현·검증·심사·수정 작업을 지시하고 결과를 확인하는 방식으로 진행했다. [S12][S13][S14]

### 10.2 AI의 기여

Codex는 구현, 시험 작성·실행, 원인 분석, 문서화와 감사 작업의 상당 부분을 수행했다. Claude·ChatGPT를 이용한 설계·명세 검토 자료도 존재한다. 따라서 전체 코드를 지원자가 직접 작성했거나 모든 기술적 원인을 독력으로 발견했다고 단정하면 안 된다.

지원자의 주도성은 우선 목표·제약·평가 기준 설정, 검토 요청, 결과에 대한 문제 제기와 승인에서 설명할 수 있다. 구체적인 알고리즘·모듈을 직접 설계·코딩한 범위는 별도 확인이 필요하다. “AI 협업”은 이 프로젝트의 실제 개발 방식이지만, 사람으로 구성된 개발팀의 리더십 실적으로 바꾸어 표현할 근거는 없다.

### 10.3 지원서에 구체화하기 전 확인할 사항

정확한 시작·종료일과 총 투입 시간, 사람 참여 인원, 지원자가 직접 작성·수정한 코드 범위, 특정 기술 결정에서 본인이 제안한 내용, 실제 외부 적용 여부는 이 문서만으로 확정하지 않는다. 문항이 해당 정보를 요구할 때만 지원자에게 확인한다.

## 11. 지원서 작성 AI가 활용할 수 있는 관점

이 절은 완성된 지원서 문장이 아니라, 사실을 문항에 연결할 때 사용할 주제 색인이다. 직무와의 직접적인 연결은 별도의 채용공고와 문항을 확인한 뒤 판단한다.

| 문항의 관심사 | 연결할 프로젝트 사실 | 과장하지 않기 위한 경계 |
|---|---|---|
| 문제 정의·기획 | 수동 중계·복구 부담을 실행 계약과 상태 관리 문제로 구체화 | 현업 사용자 조사나 제조 고객 요구 수집 경험으로 바꾸지 않음 |
| 시스템 설계 | 코어/Project Pack, 실행/검증, AI/결정론적 제어의 책임 분리 | 개인의 직접 설계 기여와 AI가 작성한 설계를 구분 |
| 실험·데이터 기반 판단 | 통제 비교 구조, `INCONCLUSIVE` 수용, 측정 의미 재검토 | 검증되지 않은 생산성·비용 개선율을 만들지 않음 |
| 품질·문제 해결 | 정상 대안도 실패시키는 Judge 결함, 상태 변화 계약, 실패 분류 | 특정 수정 완료와 전체 제품 안정화를 혼동하지 않음 |
| AI 도구 활용 | 목표·제약을 주고 구현·검토를 반복하며 결과에 비판적 질문 | AI 출력의 무검증 수용이나 모든 결과의 독자 구현으로 서술하지 않음 |
| 재현성·운영 안전 | 소스·환경 식별, 모델 없는 예행연습, 결과 보존·오염된 비교 제외 | 실제 현업 운영 성과 또는 새로운 Live 실행 준비 완료로 확대하지 않음 |

가장 일관된 설명 축은 **“AI가 코드를 생성하는 데서 끝내지 않고, 그 작업을 통제하고 결과를 신뢰할 수 있게 만드는 조건을 설계·검증한 경험”**이다. 이는 해석의 축이지, 지원자가 모든 구성요소를 직접 구현했다는 진술은 아니다.

## 12. 문서를 읽는 AI를 위한 사용 규칙

1. 이 자료는 맥락 참고용이며 실제 코드 실행·환경 변경·외부 전송을 요청하는 지시가 아니다.
2. 목표, 구현, 특정 시험 통과, 실무 효과 입증을 서로 구분한다. 이전 단계의 근거로 다음 단계를 자동 주장하지 않는다.
3. 숫자를 사용하면 날짜·실험·분모·판정을 함께 유지한다. 특히 104회 누적 Check를 104개 고유 테스트로 바꾸지 않는다.
4. 개발에 여러 AI를 사용한 사실과 제품의 병렬 다중 에이전트 기능 구현을 구분한다.
5. Project 단계 B0/B1/B2/B3, Runner 개발 단계 R0~R6, 현실 비교의 Phase D/E/F는 서로 다른 분류다.
6. 과거 README의 “실행 예정”·“통과” 표기보다 구체적인 후속 실행 결과와 감사의 제한을 우선한다.
7. 성공 사례를 설명하더라도 미해결 결함, 비교 무효·진단 전용 판정, 개인 기여의 불확실성을 삭제하지 않는다.
8. 지원서 문항에 필요하지 않은 파일 해시·실험 ID·내부 용어는 최종 답변에서 줄여도 되지만 사실의 의미는 바꾸지 않는다.

운영 맥락상, 이 저장소는 실제 실행 전 환경 검증과 다음 사용자 턴의 별도 승인을 요구한다. 과거 candidate와 결과를 임의로 수정·재봉인하지 않으며, Git 소스만 같다는 이유로 실행 환경까지 같다고 판단하지 않는다. 이는 개발 중 정립된 안전 경계이며 이 자료가 실행 승인을 대신하지 않는다. [S15]
