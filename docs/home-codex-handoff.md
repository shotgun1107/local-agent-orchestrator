# 범용 Codex 세션 오케스트레이터 — 집 PC 작업 인수인계

- 작성일: 2026-08-03
- 목적: 현재 PC에서 조사·논의한 내용을 집의 로컬 Codex 작업으로 정확하게 이어가기 위한 인수인계
- 현재 단계: 문헌조사와 문제 정의 완료, 범용 구조의 설계·구현은 아직 시작하지 않음

## 1. 사용자가 만들고 싶은 것

목표는 특정 프로젝트 전용 다중 에이전트 시스템이 아니다. 여러 프로젝트에서 재사용할 수 있는 **범용 Codex 세션 오케스트레이터**를 먼저 만들고, 실제 프로젝트를 시작할 때 범용 구조를 참조하여 얇은 프로젝트 전용 오케스트레이션 구성을 붙이는 것이다.

```text
범용 오케스트레이터
  ├─ 작업 표현과 상태 전이
  ├─ 의존성·병렬성 판단
  ├─ Codex 세션 생성·재개·종료
  ├─ 입력·출력과 산출물 전달
  ├─ 권한·충돌·안전 검사
  ├─ 결정적 테스트와 독립 검토
  ├─ 실패·중단·재시도·복구
  └─ 사용량·동시 실행 수·로그 관리
                 │
                 ▼
프로젝트 전용 구성
  ├─ 프로젝트 지식
  ├─ 역할과 작업 흐름
  ├─ 허용 경로와 도구
  ├─ 테스트 명령
  └─ 프로젝트별 완료 조건
```

범용 코어에는 `P1`, `P2`, `V1`, EU4 같은 특정 역할명과 도메인 규칙을 넣지 않는다. 프로젝트마다 필요한 역할과 흐름을 구성으로 선언한다.

## 2. 사용자 배경과 설명 수준

사용자는 소프트웨어마이스터고를 졸업해 프로그래밍과 기초 전공지식은 있지만, 대규모 시스템 실무 경험이나 분산 시스템의 깊은 지식은 많지 않다. Codex·Claude Code 같은 에이전트 활용 커뮤니티에서 `AI 오케스트라`라는 말을 접한 뒤 실제로 쓸 수 있는 구조를 조사하기 시작했다.

설명할 때는 개념을 지나치게 생략하지 말되, 논문 용어를 그대로 나열하지 않는다. 상태 머신, lease, idempotency 같은 용어는 실제 세션 실행에서 왜 필요한지 함께 설명한다.

## 4. 별도 저장소에서 확인한 기존 시도

현재 PC의 `C:\Users\SSAFY\Documents\이어서 작업`에는 EU4 모딩 프로젝트를 위한 세션 오케스트레이션 시도가 있다. 이 저장소에서 확인한 주요 아이디어는 다음과 같다.

- Brain 중심의 작업자·검수자 허브 구조
- 역할별 읽기·쓰기 경로 계약과 병렬 충돌 검사
- 작업 전후 SHA-256 스냅샷과 허용 범위 밖 변경 감사
- 세션 lease, timeout, 격리와 복구
- 완료 신호와 이벤트 기반 결과 회수
- mailbox의 claim·ack와 미완료 continuation 보존
- 입력이 작업 후 달라졌을 때 stale 판정
- 작업자와 독립된 검수 세션

이 시도는 좋은 참고 사례지만 범용 오케스트레이터의 기반이나 정답으로 간주하지 않는다. 다음 제약이 있다.

- 역할과 정책이 EU4 프로젝트에 강하게 고정됨
- 고정 세션 ID와 과거 절대경로에 의존함
- 안전하지만 수동 운영 단계가 많음
- 고정 작업 세션을 장기간 재사용해 문맥 오염 가능성이 있음
- 단일 로컬 프로젝트에 비해 컨트롤러와 운영 문서가 무거움

범용 설계에서는 검증된 메커니즘만 선택적으로 가져오고 구조를 그대로 복제하지 않는다.

## 5. 합의된 범용 폴더 책임

개별 파일 이름보다 다음 폴더 책임을 기준으로 설계한다.

```text
범용 오케스트레이터 저장소/
├─ orchestrator/   프로젝트와 무관한 실행 엔진
├─ projects/       프로젝트별 지식·역할·흐름·정책
├─ runs/           실행별 입력·작업·산출물·검수·로그
├─ workspaces/     작업 세션별 격리 작업 공간
├─ tests/          범용 엔진의 상태·복구·안전성 시험
└─ docs/           설계 근거와 운영 설명
```

### `orchestrator/`

프로젝트 지식을 모르는 범용 제어 계층이다. 작업 그래프, 상태 머신, 스케줄러, 세션 런타임, 저장소, 검증, 사용량 제한과 복구를 담당한다.

### `projects/`

프로젝트마다 달라지는 구성 계층이다. 프로젝트 설명, 역할, 워크플로, 지식, 권한, 도구, 테스트와 완료 조건을 둔다. 새 프로젝트 적용 시 범용 엔진을 포크하지 않고 이 구성만 추가하는 것이 목표다.

### `runs/`

한 번의 실행에서 생긴 사실의 정본이다. 사용자의 요청, 분해된 작업, 세션 식별자, 산출물, 테스트 결과, 검수, 상태 전이와 실패 기록을 보존한다. 채팅 기억을 실행 상태의 정본으로 사용하지 않는다.

### `workspaces/`

세션이 실제로 읽고 수정하는 격리 공간이다. 읽기 전용 작업은 같은 원본을 공유할 수 있지만, 병렬 쓰기 작업은 Git worktree나 동등한 격리 공간을 사용한 뒤 검증된 변경만 통합한다.

### `tests/`

프로젝트 제품의 테스트가 아니라 오케스트레이터 자체의 안전성을 검증한다. 잘못된 병렬 실행 차단, 중복 이벤트, 중단 복구, 권한 침범, stale 입력, 재시도와 사용량 제한을 시험한다.

## 6. 합의된 세션 구조

고정된 에이전트 조직을 항상 실행하지 않는다. 작업에 필요한 세션만 동적으로 사용한다.

```text
사용자
  ↓
오케스트레이터 프로그램 — 상태와 다음 행동의 유일한 결정권자
  ├─ 계획·조정 세션 — 요청을 작업 그래프로 변환
  ├─ 작업 세션 1~N — 독립 작업만 필요할 때 병렬 수행
  ├─ 일반 테스트·스키마·정책 검사 — AI가 아닌 코드
  └─ 독립 검토 세션 — 작업자와 분리된 새 문맥으로 판정
```

### 세션 수명 원칙

- 계획·조정 세션은 한 실행이나 마일스톤 안에서만 재사용한다.
- 작업 세션은 기본적으로 작업 단위로 새로 만들고, 같은 작업의 연속 수정에만 재개한다.
- 검토 세션은 작업자와 분리하고 가능하면 새 세션과 읽기 전용 권한을 사용한다.
- 서로 관계없는 작업에 기존 세션을 재사용하지 않는다.
- 세션 ID는 실행 기록에 저장하되 전역 설정에 영구 고정하지 않는다.
- 기본 최대 동시 작업 세션은 2개로 시작하고 실측 후 조정한다.

### 통신 원칙

세션끼리 직접 자유 대화하게 하지 않는다.

```text
작업 계약 전달
→ 세션 실행
→ 구조화된 결과와 산출물 저장
→ 결정적 검증
→ 다음 세션에 필요한 내용만 전달
```

상세 정보는 산출물에 두고 상태 메시지는 `completed`, `failed`, `blocked`, `cancelled`처럼 짧고 기계 판독 가능하게 유지한다.

## 7. 구현 원칙

1. 오케스트레이터 프로그램이 권한, 상태 전이, 병렬성, 재시도와 종료를 결정한다. AI의 자기 보고만으로 완료 처리하지 않는다.
2. 결정 가능한 것은 코드로 검증한다. 테스트, 린트, 스키마, 경로 범위, Git diff와 종료 코드는 AI 판정으로 대체하지 않는다.
3. 작업자에게 전체 저장소를 무조건 전달하지 않는다. 현재 작업, 필요한 입력, 허용 범위, 출력 계약과 완료 조건만 제공한다.
4. 병렬화는 기본값이 아니다. 정보 의존성이 없고 격리 비용보다 이득이 클 때만 사용한다.
5. Codex 세션을 첫 런타임으로 사용하되 런타임 경계를 분리해 향후 API나 다른 에이전트로 교체할 수 있게 한다.
6. 구독 사용량도 비용이다. 동시 세션, 재시도, 검토 반복과 고급 모델 승격에 명시적인 예산을 둔다.
7. 로컬 단일 사용자 도구를 먼저 완성한다. 분산 실행, 다중 사용자 서버와 범용 플러그인 생태계는 초기 범위에서 제외한다.
8. 범용성은 모든 상황을 한꺼번에 지원한다는 뜻이 아니다. 최소 공통 메커니즘과 프로젝트 확장 경계를 안정적으로 제공하는 것을 뜻한다.

## 8. 다음 작업의 권장 범위

다음 세션은 바로 대규모 코드를 작성하지 않는다. 먼저 문헌의 결론을 구현 요구사항으로 변환하고 범용 설계를 확정한다.

1. 주 문헌조사에서 상태 관리, 작업 분해, 병렬성, 복구, 검증, 인간 승인, 관찰 가능성과 비용 통제에 직접 관련된 결론을 추출한다.
2. 범용 코어와 프로젝트 전용 구성의 경계를 정한다.
3. 최소 상태 머신과 작업 계약을 정의한다.
4. Codex 세션 런타임의 생성·재개·취소·종료 인터페이스를 정의한다.
5. 단일 작업, 독립 병렬 작업, 작업 실패, 검수 실패, 사용자 판단 필요의 대표 실행 흐름을 작성한다.
6. 초기 구현 범위와 나중에 추가할 기능을 분리한다.
7. 위 결과를 새 설계 문서에 기록하고 사용자에게 쉬운 말로 설명한 뒤 구현 승인을 받는다.

초기 구현에서는 다음 정도면 충분하다.

```text
로컬 단일 사용자
Codex 계정 인증 기반 세션
실행 단위 계획 세션
최대 작업 세션 2개
독립 검토 세션 1개
SQLite 상태 저장
파일 기반 산출물
결정적 명령 검증
재시도 1회
중단 후 재개
프로젝트 구성 템플릿 1개
```

초기 단계에서 제외한다.

- 항상 실행되는 서버
- 여러 사용자의 동시 사용
- 세션끼리 직접 대화하는 자율 조직
- 역할을 무조건 여러 개 만드는 구조
- 원격 분산 큐와 Kubernetes 배포
- 복잡한 웹 대시보드
- 프로젝트마다 범용 엔진을 포크하는 방식

- 범용 실행 엔진

- 세션별 격리 작업 공간
