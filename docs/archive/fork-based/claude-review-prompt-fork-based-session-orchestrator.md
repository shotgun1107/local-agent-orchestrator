```text
당신은 AI 에이전트 오케스트레이션, 로컬 개발 도구, 워크플로 엔진, 분산 시스템, 소프트웨어 제품 계열과 개발자 경험을 함께 검토하는 독립 아키텍처 심사자다.

## 심사 대상 구조

사용자가 원하는 것은 하나의 중앙 오케스트레이터에 여러 프로젝트를 등록하는 SaaS·플랫폼 구조가 아니다.

원하는 개발·배포 계보는 다음과 같다.

1. `local-agent-orchestrator`라는 범용 로컬 세션 오케스트레이터를 독립 제품으로 먼저 개발한다.
2. 특정 실제 프로젝트의 팀·지식·업무 흐름을 범용 원본에 넣지 않는다.
3. 단일 작업, 병렬 작업, 팀 인수인계, 검증 실패, 세션 중단, 재개와 사용량을 벤치마크·시험 프로젝트로 검증한다.
4. 정확도, 소요 시간, 세션 수, 사용자 개입, 충돌, 복구 성공률과 사용량을 측정해 기준 버전을 확정한다.
5. 충분히 검증된 버전(예: v1.0)을 실제 프로젝트마다 Git fork, template 또는 복사 방식으로 분기한다.
6. 각 프로젝트용 분기본에서 그 프로젝트에 맞는 팀, 역할, 지식, 워크플로, 도구, 권한, 테스트와 완료 조건을 재구성한다.
7. 각 프로젝트 전용 오케스트레이터는 자기 대상 프로젝트만 관리하고 서로 독립적으로 실행된다.
8. 프로젝트에서 발견한 개선 중 여러 프로젝트에 공통으로 필요한 것만 범용 원본에 일반화해 되돌리고, 검증 후 새 기준 버전으로 배포한다.

관계는 포함 관계가 아니라 계보 관계다.

범용 원본 → 검증된 기준 버전 → 프로젝트 A 전용 오케스트레이터
                            → 프로젝트 B 전용 오케스트레이터
                            → 프로젝트 C 전용 오케스트레이터

## 범용 원본에서 만들려는 능력

- 작업 표현과 상태 머신
- 작업 의존성 및 병렬 실행 판단
- Codex 세션 생성·재개·취소·종료
- 팀과 역할을 정의할 수 있는 일반 메커니즘
- 세션별 최소 입력 계약과 구조화된 결과 계약
- 세션 간 직접 대화가 아닌 중앙 중계와 산출물 기반 인수인계
- 읽기·쓰기 권한과 병렬 충돌 검사
- 세션별 격리 작업 공간과 검증된 변경 통합
- 테스트·린트·스키마·Git diff 등 결정적 검증
- 작업자와 분리된 독립 검토
- timeout, retry, stale input, 중단 후 재개와 실패 복구
- 동시 세션 수, 재시도, 모델 승격과 사용량 제한
- 실행 상태, 세션, 산출물, 이벤트와 사용자 승인 기록
- 프로젝트 fork에서 교체할 수 있는 확장 경계

## 현재 생각하는 세션·팀 구조

- 일반 코드로 작성된 오케스트레이터가 유일한 상태 정본과 실행 결정권자다.
- 팀은 지속되는 논리적 단위로서 책임, 지식, 권한, 도구, 입력·출력 계약과 세션 생성 정책을 가진다.
- 세션은 팀에 영구 배치된 직원이 아니라 작업 시 생성되는 실행 인스턴스다.
- 계획 세션은 한 실행 또는 마일스톤 동안만 재사용한다.
- 작업 세션은 기본적으로 작업 단위로 새로 만들고 같은 작업의 수정에만 재개한다.
- 검토 세션은 작업자와 분리된 새 문맥과 읽기 전용 권한을 기본으로 한다.
- 팀장 세션은 팀 내 독립 작업이 많고 결과 통합에 판단이 필요할 때만 임시로 만든다.
- 팀과 세션은 서로 직접 자유 대화하지 않는다. 오케스트레이터가 작업 계약, 산출물, 검증 결과와 구조화된 요약만 전달한다.
- 실행 계층은 Project → Run → Team → Task → Attempt → Session으로 생각하고 있다.
- 읽기 전용 작업은 필요한 경우 같은 원본을 공유할 수 있지만, 병렬 쓰기는 Git worktree 또는 동등한 격리 환경에서 수행한다.
- 기본 최대 동시 작업 세션은 2개, 작업 재시도는 1회로 시작하는 방안을 생각하고 있다.
- 초기에는 로컬 단일 사용자와 소프트웨어 프로젝트를 우선하며, 다중 사용자 서버·분산 큐·복잡한 웹 UI는 제외한다.

## 중요한 비용 전제

개인이 API 종량제 비용을 지속적으로 감당하기 어렵기 때문에 Codex 계정 인증 기반 로컬 세션을 주 실행 수단으로 생각하고 있다. 그러나 구독 사용량도 제한된 자원이므로 세션 수를 늘리는 것을 성공으로 보지 않는다. 동일 품질을 더 적은 세션, 더 적은 재시도와 더 적은 사용자 중계로 달성하는 것이 목표다.

Codex의 현재 기능·인증·SDK·세션 동작에 대한 사실을 평가에 사용한다면 현재 공식 OpenAI 문서를 확인하고 링크를 붙여라. 제품 동작을 추측하지 마라. 공식 문서로 확인되지 않는 Desktop 세션 가시성, 계정 사용량 처리나 자동화 특성은 ‘미확인’으로 표시하라.

## 반드시 검토할 핵심 질문

1. 내가 설명한 구조를 먼저 당신의 말로 재구성하라. 특히 “하나의 엔진에 여러 프로젝트를 등록”하는 구조와 “검증된 원본을 프로젝트별로 fork”하는 구조의 차이를 분명히 설명하라.
2. 범용 원본을 완성한 뒤 프로젝트별 전체 저장소를 fork·복사하는 방식이 실제 유지보수에 적합한가?
3. GitHub fork, template repository, 코드 복사, 공용 core package + 프로젝트별 얇은 저장소, plugin 구조를 비교하라.
4. 사용자의 의도를 유지하면서 fork drift와 upstream 병합 비용을 줄일 수 있는 구조가 있는가? 하이브리드가 낫다면 구체적으로 제안하라.
5. 범용 원본에 남겨야 할 책임과 프로젝트 분기본으로 옮겨야 할 책임의 경계를 평가하라.
6. 팀은 지속되고 세션은 작업마다 생성되는 구조가 품질·비용·컨텍스트 관리 측면에서 타당한가?
7. 팀장 세션, 계획 세션, 작업 세션과 검토 세션이 언제 필요하고 언제 낭비인지 판단 기준을 제시하라.
8. 세션 간 직접 통신을 금지하고 오케스트레이터가 산출물과 계약을 중계하는 방식의 장단점을 평가하라.
9. 일반 코드가 상태·권한·테스트·재시도·사용량을 결정하고 AI는 계획·작업·검토만 담당하는 경계가 적절한가?
10. 프로젝트별 fork가 실제 대상 프로젝트와 별도 저장소로 존재하는 방식과 프로젝트 내부에 포함되는 방식을 비교하라.
11. 이 구조가 지나치게 무거워지는 지점을 찾고, MVP에서 반드시 빼야 할 것을 지정하라.
12. 범용 원본의 성능을 실제 프로젝트 fork 전에 어떻게 검증해야 하는가? 비교 기준선과 실패 기준까지 제안하라.
13. 단일 세션과 비교했을 때 다중 세션·팀 구조가 실제로 이득인지 어떤 실험으로 판정할지 설계하라.
14. 보안, Git 변경, 비밀정보, 작업 공간 격리, 중단 복구에서 빠진 치명적 문제가 있는지 확인하라.
15. 사용자가 놓친 더 단순하거나 실용적인 대안이 있다면 의도에 맞지 않는다고 숨기지 말고 설명하라.

## 평가 원칙

- 제안자의 표현을 그대로 반복하지 말고 독립적으로 판단하라.
- 좋은 점보다 실패 가능성과 운영 비용을 구체적으로 찾는 데 우선순위를 둬라.
- 개념적으로 가능하다는 말과 개인이 실제로 만들고 운영하기 좋은지를 구분하라.
- 특정 AI 오케스트레이션 프레임워크 안에서만 보지 말고, 워크플로 엔진, 빌드 시스템, CI, 소프트웨어 제품 계열, reference architecture, template repository, plugin architecture, control plane/data plane과 분산 시스템의 교훈도 사용하라.
- 근거가 문헌 또는 공식 문서인지, 일반적인 설계 판단인지, 당신의 추론인지 구분하라.
- 확인하지 못한 것은 미확인이라고 쓰고 추측으로 채우지 마라.
- 사용자의 의도와 다른 구조를 권한다면 왜 더 낫고 무엇을 포기하는지 명확히 설명하라.
- 아직 구현하지 않았으므로 기존 코드와의 호환성을 핑계로 잘못된 구조를 유지하지 마라.

## 출력 형식

### 1. 내가 이해한 목표
비전공 실무 입문자도 이해할 수 있게 전체 구조와 개발·fork·운영 흐름을 설명하라.

### 2. 구조도와 실제 실행 예시
범용 원본에서 프로젝트 fork가 만들어지는 계보와, 한 프로젝트 fork가 세션을 실행하는 과정을 각각 보여라.

### 3. 타당한 판단
유지할 설계와 그 이유를 정리하라.

### 4. 주요 문제와 실패 가능성
심각도 `치명적 / 높음 / 중간 / 낮음`으로 분류하고 발생 조건과 영향을 설명하라.

### 5. 배포·확장 방식 비교
다음 방식을 표로 비교하라.

- 전체 Git fork
- template repository 또는 복사
- 공용 core package + 프로젝트별 전용 저장소
- plugin 또는 adapter 구조
- 하나의 멀티프로젝트 플랫폼

사용자 의도에 가장 가까우면서 유지보수 가능한 방식을 하나 권고하라.

### 6. 권고 아키텍처
범용 원본과 프로젝트 전용 분기본의 폴더 책임, 변경 가능 경계와 upstream 반영 흐름을 제시하라. 개별 파일 목록보다 폴더 책임과 프로세스를 중심으로 설명하라.

### 7. 팀과 세션 운영 모델
팀 생성, 작업 분해, 세션 생성, 결과 중계, 검증, 재작업, 통합과 종료까지 순서대로 설명하라.

### 8. 성능 검증 계획
단일 세션 기준선, 다중 세션 실험, 측정 지표, 시험 작업, 합격·중단 기준을 제시하라.

### 9. 현실적인 MVP
개인이 먼저 구현할 최소 범위와 명시적으로 뒤로 미룰 기능을 구분하라.

### 10. 최종 판정
`그대로 진행 / 수정 후 진행 / 구조 재검토` 중 하나를 선택하고 가장 중요한 이유 세 가지를 적어라.

### 11. 사용자에게 확인할 질문
결과를 크게 바꾸는 질문만 최대 5개 제시하라. 질문 없이도 합리적으로 판단할 수 있는 것은 스스로 판단하라.

분량을 억지로 줄이지 말되 같은 설명을 반복하지 마라. 이번 답변의 목표는 칭찬이나 구현 시작이 아니라 사용자와 설계자의 인식 차이를 찾고, 실제로 만들 가치가 있는 구조로 교정하는 것이다.
```
