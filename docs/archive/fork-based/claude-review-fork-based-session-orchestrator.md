- 심사일: 2026-08-04
- 심사 대상: `docs/archive/fork-based/claude-review-prompt-fork-based-session-orchestrator.md`의 ‘심사 대상 구조’
- 읽은 자료: 주 문헌조사(1,242줄), 보조 문서 동결 헤더·목차·관련 절, `codex-revision-log.md`, `home-codex-handoff.md`

## 0. 먼저 말해야 할 것

이 심사에서 가장 중요한 발견은 구조 비교가 아니다. **당신이 만들려는 기능의 상당 부분을 Codex가 이미 제품으로 제공하고 있다.** 공식 문서에서 확인한 것만 나열하면 세션 생성·재개, 세션별 읽기/쓰기 권한, 병렬 서브에이전트, Git worktree 격리, 훅, 프로젝트별 지식 파일이 모두 이미 있다.

이건 당신 계획이 틀렸다는 뜻이 아니다. **만들어야 할 범위가 생각보다 훨씬 작다는 뜻이고, 그건 1인 개발자에게 좋은 소식이다.** 다만 이 사실을 모르고 설계하면 3~6개월 동안 이미 있는 것을 다시 만들게 된다.

두 번째로 중요한 것: **당신의 비용 전제 전체가 아직 검증되지 않았다.** "Codex 계정 인증 기반 로컬 세션을 주 실행 수단으로" 쓰겠다는 것이 이 프로젝트의 경제적 토대인데, Codex SDK로 프로그램에서 세션을 돌릴 때 그 사용량이 구독으로 처리되는지 API 종량제로 처리되는지 나는 확인하지 못했다. 이것 하나에 프로젝트 성립 여부가 걸려 있다. 11절 첫 번째 질문이다.

## 1. 내가 이해한 목표

### 1.1 한 문장 요약

여러 개의 Codex 세션을 사람이 일일이 붙잡고 지시하는 대신, **일반 코드로 짠 프로그램이 작업을 쪼개고 세션에 맡기고 결과를 검사하고 실패하면 다시 시키는** 구조를 만들되, 그 프로그램을 특정 프로젝트 전용이 아니라 **범용 원본으로 먼저 완성한 뒤 프로젝트마다 복제해서 고쳐 쓰겠다**는 것이다.

### 1.2 왜 이런 게 필요한가 — 처음 보는 개념 설명

**오케스트레이터(orchestrator)**는 지휘자다. 연주자(AI 세션)에게 악보(작업 계약)를 나눠주고, 언제 시작하고 멈출지 정하고, 틀리면 다시 시킨다. 핵심은 **지휘자가 AI가 아니라 일반 프로그램**이라는 점이다. 왜 그래야 하는지는 당신 문헌조사가 이미 답을 갖고 있다 — 주 문서 법칙 1과 §9.2의 운영 조사(68%가 사람 개입 전 10단계 이하)는 "AI에게 상태 관리와 종료 판단을 맡기면 신뢰성이 떨어진다"는 쪽을 지지한다.

**상태 머신(state machine)**은 "작업이 지금 어느 칸에 있는가"를 정해진 칸과 정해진 이동 규칙으로만 관리하는 것이다. `대기 → 실행중 → 검증중 → 완료` 같은 칸을 만들고, `대기`에서 바로 `완료`로 못 뛰게 막는다. 이게 필요한 이유는 단순하다. AI가 "다 했습니다"라고 말해도 그건 주장일 뿐이고, 테스트가 통과해야 진짜 `완료`이기 때문이다.

**멱등성(idempotency)**은 같은 걸 두 번 해도 결과가 같은 성질이다. 세션이 죽어서 재시도했는데 이미 파일이 반쯤 고쳐져 있다면, 두 번째 시도가 첫 번째 결과를 망가뜨리면 안 된다.

**Stale input(낡은 입력)**은 세션 A가 파일을 읽고 작업하는 동안 세션 B가 그 파일을 바꿔버린 상황이다. A의 결과는 이미 존재하지 않는 세계를 전제로 한 것이라 버려야 한다. 병렬 실행을 하는 순간 반드시 생기는 문제다.

**Git worktree**는 같은 저장소를 여러 폴더에 동시에 펼쳐놓는 Git 기능이다. 세션 두 개가 같은 파일을 동시에 고치면 서로 덮어쓰니까, 각자 다른 폴더에서 일하게 하고 검증된 것만 합친다.

**Fork drift(포크 표류)**는 원본을 복제해서 각자 고치다 보면 시간이 지날수록 서로 달라져서, 원본의 수정을 복제본에 반영하기가 점점 어려워지는 현상이다. 이번 심사의 핵심 쟁점이다.

### 1.3 두 구조의 차이 — 당신이 요청한 대비

**(A) 하나의 엔진에 여러 프로젝트를 등록하는 구조**

```
orchestrator-repo/
├─ orchestrator/          엔진 코드 (1벌)
└─ projects/
   ├─ eu4-mod/            프로젝트 A 설정
   ├─ my-webapp/          프로젝트 B 설정
   └─ side-project/       프로젝트 C 설정
```

엔진이 한 벌이고, 프로젝트는 설정 폴더로 들어온다. 새 프로젝트를 추가하면 `projects/` 아래에 폴더가 하나 늘어난다. 엔진을 고치면 모든 프로젝트에 즉시 반영된다. 대신 프로젝트들이 한 저장소를 공유한다.

**(B) 검증된 원본을 프로젝트별로 fork하는 구조 (당신이 원하는 것)**

```
local-agent-orchestrator (원본, v1.0)
        │ fork
        ├──→ orchestrator-for-eu4      (독립 저장소, 자유롭게 개조)
        ├──→ orchestrator-for-webapp   (독립 저장소, 자유롭게 개조)
        └──→ orchestrator-for-side     (독립 저장소, 자유롭게 개조)
```

각 프로젝트가 **엔진 코드까지 통째로 복제본**을 갖는다. 프로젝트 A에서 엔진을 마음대로 뜯어고쳐도 B는 영향받지 않는다. 대신 원본을 고쳤을 때 그 수정을 A·B·C에 각각 손으로 반영해야 한다.

**핵심 차이는 "설정만 다른가, 코드까지 다른가"다.** (A)는 코드 1벌 + 설정 N벌, (B)는 코드 N벌.

### 1.4 당신이 실제로 원하는 것에 대한 내 판단

인수인계 문서(`home-codex-handoff.md`) 8절은 제외 목록에 **"프로젝트마다 범용 엔진을 포크하는 방식"**을 명시적으로 적어놨다. 그런데 이번 프롬프트는 정반대를 요구한다. 이건 단순한 변심이 아니라 **문제 인식이 바뀐 것**으로 보이고, 그 바뀐 인식 자체는 타당하다.

내가 추측하는 당신의 진짜 걱정은 이것이다.

> "프로젝트마다 필요한 게 너무 달라서, 설정 파일만으로는 절대 안 맞춰질 것 같다. 억지로 범용 설정 스키마를 만들면 결국 아무 프로젝트에도 안 맞는 괴물이 된다. 차라리 복사해서 그 프로젝트에 맞게 코드를 직접 고치는 게 낫다."

**이 걱정은 정당하다.** 설정으로 모든 것을 표현하려는 시도는 실제로 자주 실패한다. 다만 당신은 (A)를 "SaaS·멀티테넌트 플랫폼"으로 이해했고 그래서 거부했는데, 실제로 인수인계 문서의 `projects/` 구조는 플랫폼이 아니라 그냥 한 저장소 안의 설정 폴더였다. **당신은 "설정만으로는 부족하다"는 옳은 직관 때문에, "한 저장소를 쓴다"는 별개의 것까지 함께 버렸다.**

그리고 이 둘 사이에 5절에서 다룰 세 번째 선택지가 있다.

## 2. 구조도와 실제 실행 예시

### 2.1 원본에서 프로젝트 fork가 나오는 계보

```
[1단계] 범용 원본 개발
   local-agent-orchestrator
   - 작업 상태 머신, Run 원장, 세션 런타임 경계
   - 검증 게이트, 재시도, 사용량 기록
   - 프로젝트 지식 없음. EU4도 웹앱도 모름

[2단계] 벤치마크 프로젝트로 검증
   시험 과제 N개 실행 → 성공률·시간·세션 수·개입 횟수 측정
   기준 통과 → v1.0 태그

[3단계] 실제 프로젝트에 분기
   v1.0 ──fork──→ orchestrator-for-eu4
              └──→ orchestrator-for-webapp

[4단계] 각 분기본에서 개조
   EU4용: 모딩 파일 구조, 게임 실행 검증, 로컬라이제이션 규칙
   웹앱용: 프론트/백 분리, e2e 테스트, 스키마 마이그레이션 검사

[5단계] 공통 개선만 원본으로 역류
   "중단 후 재개가 깨지는 버그" → 원본 수정 → v1.1
   "EU4 파일 인코딩 처리" → 원본에 넣지 않음
```

### 2.2 한 프로젝트 분기본이 세션을 실행하는 과정

`orchestrator-for-webapp`에서 "로그인 API에 rate limit을 추가하고 테스트를 붙여라"를 실행할 때.

```
사용자 요청
   ↓
[오케스트레이터 = 일반 프로그램]
   ↓
① Run 생성 — SQLite에 run_id, 요청 원문, 시작 시각 기록
   ↓
② 작업 분해
   T1 현재 미들웨어 구조 파악      (읽기 전용)
   T2 rate limit 구현              (쓰기, T1 의존)
   T3 테스트 작성                  (쓰기, T2 의존)
   T4 독립 검토                    (읽기 전용, T3 의존)
   → 전부 순차 의존. 병렬 불가로 판정하고 세션 1개만 사용
   ↓
③ T1 실행
   Codex thread 생성 (sandbox=read_only)
   입력 계약: 대상 경로, 답해야 할 질문, 출력 스키마
   결과를 runs/<run_id>/T1.json 에 저장
   상태: 실행중 → 완료
   ↓
④ T2 실행
   T1 결과 요약만 전달 (T1의 대화 로그 전체를 넘기지 않음)
   Codex thread 생성 (sandbox=workspace_write)
   작업 공간: git worktree로 격리
   ↓
⑤ 결정적 검증 — AI 아님
   git diff 가 허용 경로 안에 있는가
   lint 통과하는가
   기존 테스트가 깨지지 않는가
   → 실패하면 T2를 같은 thread에서 1회 재개(재시도)
   → 또 실패하면 상태를 blocked 로 두고 사용자에게 보고
   ↓
⑥ T3 실행 → 검증 (새 테스트가 실제로 실패하는 것을 잡는지 확인)
   ↓
⑦ T4 독립 검토
   새 thread, sandbox=read_only, T2·T3의 대화 이력 없이 diff만 전달
   → 문헌조사 법칙 7(검증기는 생성기와 다른 실패 모드를 가져야 한다)의 구현
   ↓
⑧ 통합
   worktree의 변경을 main에 병합
   Run 상태 completed, 총 세션 수·토큰·소요 시간 기록
```

여기서 **⑤가 이 시스템의 존재 이유**다. AI가 "구현했습니다"라고 말하는 것과 테스트가 통과하는 것은 다른 사건이고, 그 둘을 구분하는 게 오케스트레이터의 핵심 가치다.

## 3. 타당한 판단

칭찬이 아니라, 바꾸지 말아야 할 것을 짚는 절이다.

**3.1 일반 코드가 상태·권한·검증·종료를 결정한다 — 유지**

이건 이 설계에서 가장 중요하고 가장 옳은 판단이다. 문헌조사 법칙 1이 지지하고, §9.2의 운영 조사(74%가 사람 평가에 의존, 신뢰성이 최대 과제)와 §9.5의 LLM 심판 한계(체계적 문제 9개 중 2개만 포착, 운영 게이트 100라운드 중 0건 표시)가 뒷받침한다. AI에게 "다 했니?"를 묻지 않는 구조는 근거가 충분하다.

**3.2 세션 간 직접 대화 금지, 산출물과 계약으로 중계 — 유지**

문헌조사 법칙 3(대화보다 상태를 먼저 설계하라)과 §5.2 MAS-BENCH의 실패 유형(공유 상태 일관성, 규약 합의, 일관된 종료)이 직접 지지한다. 특히 MAS-BENCH의 개선책 CAMOC이 "조기 전역 메타데이터 교환 + 단일 커밋 검증"으로 성공률을 크게 올렸다는 점은 당신 설계와 같은 방향이다. Codex 공식 문서도 서브에이전트가 원본 출력이 아니라 **요약(summaries)**을 반환해야 한다고 명시한다.

**3.3 병렬화를 기본값으로 두지 않음 — 유지**

문헌조사 §9.1(순차 의존 과제에서 다중 에이전트가 최대 70% 악화, 독립 에이전트 오류 증폭 17.2배)과 Codex 공식 문서의 경고("병렬 쓰기 워크플로는 더 주의하라. 동시에 코드를 편집하는 에이전트는 충돌과 조정 오버헤드를 만든다")가 양쪽에서 같은 말을 한다. 기본 동시 세션 2개는 보수적이고 적절하다.

**3.4 검토 세션을 작업자와 분리하고 읽기 전용으로 — 유지**

법칙 7의 정확한 구현이고, 뒤에 나오듯 Codex가 이미 `sandbox=read_only`를 턴 단위로 지원하므로 구현 비용도 거의 없다.

**3.5 세션을 영구 직원이 아니라 작업 단위 인스턴스로 — 유지**

Codex 공식 문서가 설명하는 **context rot**(대화가 길어질수록 관련 없는 내용이 쌓여 성능이 떨어짐)에 대한 올바른 대응이다. 인수인계 문서가 EU4 시도의 문제로 "고정 작업 세션 장기 재사용으로 인한 문맥 오염"을 지적한 것도 같은 관찰이다.

**3.6 구독 사용량을 비용으로 취급하고 세션 수 증가를 성공으로 보지 않음 — 유지**

문헌조사 법칙 12(단일 목표 최적화 금지)와 §14.6(총 예산을 통제하지 않으면 '에이전트가 많아서 좋아진 것'과 '추론 예산을 더 써서 좋아진 것'을 구분할 수 없다)에 정확히 부합한다. Codex 문서도 "서브에이전트 워크플로는 비슷한 단일 에이전트 실행보다 토큰을 더 쓴다"고 명시한다.

## 4. 주요 문제와 실패 가능성

### 치명적

**[치명적-1] 비용 전제가 검증되지 않았다**

- **내용**: 이 프로젝트의 경제적 토대는 "API 종량제는 개인이 못 버티니 Codex 계정 인증 기반 로컬 세션을 쓴다"이다. 그런데 Codex SDK(`@openai/codex-sdk`, `openai-codex`)로 프로그램에서 스레드를 생성할 때 그 사용량이 ChatGPT 구독으로 처리되는지, API 키 종량제로 처리되는지를 **나는 확인하지 못했다(`미확인`)**.
- **발생 조건**: 항상. 전제 자체의 문제다.
- **영향**: 만약 SDK 경로가 API 과금이라면 "구독으로 로컬 세션을 돌린다"는 계획 전체가 성립하지 않는다. 오케스트레이터를 다 만든 뒤에 알게 되면 수개월이 낭비된다.
- **조치**: 코드 한 줄 쓰기 전에 확인하라. 확인 방법은 11절 질문 1에 적었다.

**[치명적-2] Fork drift가 1인 유지보수 한계를 넘는다**

- **내용**: 프로젝트 3개를 fork하면 저장소가 4개(원본 + 3)가 된다. 원본에서 "중단 후 재개가 깨지는 버그"를 고치면 3개 분기본에 각각 병합해야 하고, 각 분기본은 이미 그 파일을 고쳐놨을 가능성이 높으므로 충돌이 난다.
- **발생 조건**: 프로젝트 2개 이상 + 원본 수정 1회 이상. 즉 거의 확실히 발생한다.
- **영향**: 1인 개발자 기준으로 예상되는 결말은 셋 중 하나다. (a) 병합을 포기하고 각 fork가 독립 제품이 된다 — 그러면 "범용 원본"을 만든 의미가 사라진다. (b) 병합 부담 때문에 원본을 고치지 않게 된다 — 개선이 멈춘다. (c) 유지보수에 개발보다 많은 시간을 쓴다.
- **왜 심각한가**: 이건 능력이나 성실성 문제가 아니라 구조적 비용이다. 오픈소스 프로젝트가 fork 대신 플러그인·패키지 버전으로 확장을 처리하는 이유가 이것이다.
- **조치**: 5절 비교표와 6절 권고안 참조. 당신의 목표(프로젝트별 독립성)는 fork 없이도 달성 가능하다.

### 높음

**[높음-3] Codex가 이미 제공하는 기능을 다시 만들려 하고 있다**

공식 문서에서 확인한 중복은 다음과 같다.

| 당신이 만들려는 것 | Codex가 이미 제공 | 출처 |
|---|---|---|
| 세션 생성·재개·종료 | `codex.startThread()`, `thread.run()`, `codex.resumeThread(threadId)` | [SDK](https://developers.openai.com/codex/sdk) |
| 세션별 읽기·쓰기 권한 | `Sandbox.read_only` / `workspace_write` / `full_access`, **턴 단위로도 변경 가능** | [SDK](https://developers.openai.com/codex/sdk) |
| 병렬 작업 세션 | 서브에이전트 워크플로 (병렬 스폰, 요약 반환, `/agent`로 스레드 전환) | [Subagents](https://developers.openai.com/codex/concepts/subagents) |
| 세션별 격리 작업 공간 | Codex App의 Worktrees | [Worktrees](https://developers.openai.com/codex/app/worktrees) `세부 미확인` |
| 세션 전후 훅 | Hooks | [Hooks](https://developers.openai.com/codex/hooks) `세부 미확인` |
| 프로젝트별 지식 주입 | `AGENTS.md`, Skills, Plugins | [AGENTS.md](https://developers.openai.com/codex/guides/agents-md) `세부 미확인` |
| 세션별 모델·추론 강도 지정 | 에이전트 파일의 `model`, `model_reasoning_effort` | [Subagents](https://developers.openai.com/codex/concepts/subagents) |

특히 **검토 세션 읽기 전용**은 공식 문서에 예제까지 있다.

```python
thread = codex.thread_start(sandbox=Sandbox.workspace_write)
thread.run("Make the requested change.")
review = thread.run("Review the diff only.", sandbox=Sandbox.read_only)
```

- **영향**: 이걸 모르고 설계하면 MVP가 3~6개월로 늘어나고, Codex가 업데이트될 때마다 직접 만든 계층이 깨진다.
- **조치**: 6절 권고안은 이 중복을 제거한 범위로 다시 그렸다.

**[높음-4] "실제 프로젝트 없이 v1.0을 검증한다"는 순서가 성립하지 않는다**

- **내용**: 계획 3~4단계는 벤치마크·시험 프로젝트로 범용 원본을 검증하고 기준 버전을 확정한 뒤 실제 프로젝트에 분기한다. 그런데 **범용성은 실제로 서로 다른 프로젝트에 적용해봐야만 검증된다.** 시험 프로젝트는 당신이 만든 것이므로 당신의 엔진에 맞게 생기기 마련이다.
- **발생 조건**: 항상.
- **영향**: v1.0이 "검증됐다"고 선언한 뒤 첫 실제 프로젝트에서 근본 가정이 깨지면, 이미 fork한 저장소들을 전부 다시 고쳐야 한다. 순서상 가장 비싼 시점에 문제가 드러난다.
- **조치**: 실제 프로젝트 1개를 **동시에** 진행하라. 범용화는 두 번째 프로젝트가 생겼을 때 시작하는 것이 안전하다. "두 사례가 생기기 전까지 추상화하지 않는다"는 것은 소프트웨어 설계의 일반 원칙이고, 여기에 특히 잘 맞는다.

**[높음-5] 6계층 실행 모델이 1인 로컬 도구에 과하다**

- **내용**: `Project → Run → Team → Task → Attempt → Session`. 6계층은 다중 사용자 SaaS의 계층 수다.
- **영향**: 계층마다 상태·저장·조회·복구 코드가 필요하다. 특히 `Team`은 MVP에서 아무 일도 하지 않으면서 모든 쿼리와 상태 전이에 끼어든다.
- **조치**: MVP는 `Run → Task → Attempt → Session` 4계층으로 시작하라. `Project`는 저장소가 분리되면 자동으로 표현되고, `Team`은 필요성이 실증된 뒤에 넣어라.

**[높음-6] 병렬 쓰기 충돌과 stale input 처리가 설계에서 가장 어려운 부분인데 가볍게 다뤄져 있다**

- **내용**: "병렬 쓰기는 worktree로 격리한다"까지는 맞다. 그런데 격리한 두 변경을 **합칠 때** 충돌하면 어떻게 되는지, 세션 A가 읽은 파일을 세션 B가 바꿨을 때 A의 결과를 어떻게 무효화하는지가 정의돼 있지 않다.
- **발생 조건**: 동시 쓰기 세션 2개 이상 + 파일 겹침.
- **영향**: 조용한 오류가 생긴다. 두 변경이 각자 테스트를 통과했는데 합치면 깨지는 상황이 가장 나쁘다. 검증을 통과했다는 기록이 남아 있어서 원인 추적이 어렵다.
- **조치**: MVP에서는 **병렬 쓰기를 아예 금지**하라. 읽기 전용 병렬만 허용한다. 문헌조사 §9.1과 Codex 문서가 둘 다 같은 방향을 권한다. 병렬 쓰기는 8절 실험에서 이득이 실측된 뒤에 연다.

### 중간

**[중간-7] `Team`은 조기 추상화다**

팀에 "책임, 지식, 권한, 도구, 입력·출력 계약, 세션 생성 정책"을 부여한다는 설계는, 실제로는 **작업 유형(task type)** 하나로 표현되는 것을 조직 은유로 부풀린 것에 가깝다. "프론트엔드 팀"이 필요한 게 아니라 "프론트엔드 파일을 고치는 작업에는 이 검증 명령과 이 경로 범위를 쓴다"가 필요한 것이다. 문헌조사 §15 오해 1(역할 이름만 다르고 모델·정보·도구가 같으면 실질적 전문성이 아니다)이 정확히 이 지점을 경고한다.

**[중간-8] 팀장 세션은 근거가 없다**

"팀 내 독립 작업이 많고 결과 통합에 판단이 필요할 때만 임시로" 만든다고 했는데, 그 판단을 왜 오케스트레이터 코드나 검토 세션이 못 하는지가 설명되지 않는다. 이건 문헌조사에서 내가 법칙 9를 `근거 부족`으로 판정한 것과 같은 문제다 — 조직 은유에서 온 계층인데 실증이 없다. **MVP에서 빼라.** 통합 판단이 실제로 어려운 사례가 3번 이상 관측되면 그때 넣어라.

**[중간-9] 계획 세션이 실제로 필요한지 검증되지 않았다**

요청을 작업 그래프로 바꾸는 일을 AI에게 맡기는데, 초기에는 당신이 직접 작업을 나누는 게 더 빠르고 정확할 가능성이 높다. 계획 세션은 세션 1개를 항상 소비하고, 계획이 틀리면 하류 작업이 전부 잘못된다. MVP에서는 **사람이 작업을 정의하고 오케스트레이터가 실행만** 하는 형태로 시작한 뒤, 계획 자동화의 이득을 따로 측정하라.

**[중간-10] 비밀정보와 `full_access` 취급이 정의돼 있지 않다**

세션이 `.env`, 토큰, API 키를 읽을 수 있는가? worktree에 비밀 파일이 복사되는가? Codex의 `Sandbox.full_access`는 파일시스템 제한 없이 실행되므로, 편의를 위해 이걸 쓰기 시작하면 격리 설계 전체가 무의미해진다. 문헌조사 법칙 11(권한은 위임 사슬 전체에서 감소해야 한다)과 §11.1(간접 프롬프트 주입)이 관련된다. 특히 **AI가 읽는 파일 안의 문장이 지시로 작동할 수 있다**는 점을 기억하라 — 외부에서 받은 코드나 이슈 텍스트를 세션에 넣을 때 위험하다.

### 낮음

**[낮음-11] 기본값(동시 2세션, 재시도 1회)에 근거가 없다** — 다만 보수적인 방향이라 시작점으로는 무해하다. 8절에서 실측 후 조정하면 된다.

**[낮음-12] Run 기록의 보존·정리 정책이 없다** — 실행마다 worktree와 로그가 쌓이면 디스크가 찬다. 자동 정리 규칙을 나중에 넣어라.

## 5. 배포·확장 방식 비교

| 방식 | 프로젝트별 자유도 | 원본 개선 반영 | 버전 고정 | 1인 유지보수 부담 | 초기 구축 비용 | 당신 의도 부합 |
|---|---|---|---|---|---|---|
| **전체 Git fork** | 최고 (코드까지 마음대로) | 수동 병합, 충돌 잦음 | 불가 (분기가 곧 버전) | **매우 높음** (N배) | 낮음 | 높음 |
| **template repo / 복사** | 최고 | **사실상 불가** (연결 없음) | 불가 | 중간 (반영 포기 전제) | 매우 낮음 | 높음 |
| **공용 core 패키지 + 프로젝트별 얇은 저장소** | 높음 (설정 + 훅 + 필요시 core 확장) | `버전 올리기` 한 줄 | **가능** (A는 1.0, B는 1.2) | **낮음** | 중간 | **높음** |
| **plugin / adapter 구조** | 중간 (확장점 안에서만) | 자동 | 가능 | 낮음 | **높음** (확장점 설계가 어려움) | 중간 |
| **하나의 멀티프로젝트 플랫폼** | 낮음 (설정으로만) | 자동 | 불필요 | 낮음 | 중간 | **낮음** (당신이 거부한 구조) |

### 권고: 공용 core 패키지 + 프로젝트별 얇은 저장소

**이유는 당신의 목표를 포기하지 않고 [치명적-2]만 제거하기 때문이다.**

당신이 원한 것은 두 가지였다.

1. 프로젝트마다 독립적으로 실행되고 서로 간섭하지 않을 것
2. 프로젝트마다 필요한 것을 자유롭게 바꿀 수 있을 것
3. 관계가 포함이 아니라 **계보**일 것

패키지 방식은 셋 다 만족한다.

```
local-agent-orchestrator-core   (파이썬 패키지, 버전 1.0 / 1.1 / 1.2 ...)
        │
        │ pip install local-agent-orchestrator-core==1.0
        ↓
orchestrator-for-eu4/           ← 완전히 독립된 저장소
├─ pyproject.toml               core==1.0 고정
├─ config/                      경로, 검증 명령, 완료 조건
├─ hooks/                       이 프로젝트만의 파이썬 코드
└─ runs/                        이 프로젝트의 실행 기록
```

- **독립성**: 저장소가 완전히 분리된다. EU4용을 아무리 고쳐도 웹앱용은 모른다. fork와 동일하다.
- **계보**: `core==1.0`이라는 선언이 곧 계보다. 어느 기준 버전에서 갈라져 나왔는지가 fork보다 **더 명시적으로** 기록된다.
- **자유도**: 설정으로 부족하면 `hooks/`에 파이썬 코드를 직접 쓴다. core의 클래스를 상속해서 갈아끼울 수도 있다. fork의 자유도 대부분을 얻는다.
- **개선 반영**: `core==1.1`로 한 줄 바꾸고 테스트를 돌린다. 병합 충돌이 없다.
- **버전 고정**: fork가 못 하는 것이다. EU4 프로젝트는 1.0에 머물고 웹앱만 1.2로 올릴 수 있다.

**포기하는 것**: core 내부를 직접 수정할 수 없다. 이때는 (a) core에 확장점을 추가해 1.x로 올리거나 (b) 정말 그 프로젝트에만 필요하면 해당 클래스를 상속해 덮어쓴다. 실무에서 (b)로 해결되지 않는 경우는 드물고, 안 되면 그건 core에 확장점이 필요하다는 신호다.

**초기에는 패키지로 게시할 필요도 없다.** `pip install -e ../local-agent-orchestrator-core` 로컬 설치나 git 태그 참조로 시작하면 된다. PyPI 게시는 나중 문제다.

## 6. 권고 아키텍처

### 6.1 core 저장소의 폴더 책임

```
local-agent-orchestrator-core/
├─ core/
│  ├─ ledger/        Run·Task·Attempt·Session 상태와 이력 (SQLite)
│  ├─ policy/        상태 전이 규칙, 재시도 정책, 예산 한도
│  ├─ runtime/       Codex SDK 어댑터 (세션 = 교체 가능한 경계)
│  ├─ verify/        결정적 검증 게이트 실행기
│  ├─ contract/      작업 입력·출력 스키마 정의와 검증
│  └─ extend/        프로젝트가 갈아끼울 수 있는 확장점 (추상 클래스)
├─ tests/            오케스트레이터 자체의 안전성 시험
└─ docs/
```

**변경 가능 경계**: 프로젝트 분기본이 건드려도 되는 것은 `core/extend/`가 정의한 확장점뿐이다. 나머지는 core만 바꾼다. 이 경계가 명확할수록 버전 업그레이드가 안전하다.

`core/runtime/`을 따로 둔 이유는 중요하다. **Codex는 지금도 빠르게 바뀌고 있다.** 이번 심사만으로도 서브에이전트·워크트리·훅·플러그인이 새로 보였다. 런타임을 하나의 인터페이스 뒤에 두면 Codex가 바뀌거나 다른 도구로 옮길 때 그 파일만 고치면 된다.

### 6.2 프로젝트 저장소의 폴더 책임

```
orchestrator-for-<project>/
├─ pyproject.toml    core 버전 고정
├─ config/
│  ├─ paths.yaml     허용 읽기·쓰기 경로
│  ├─ verify.yaml    이 프로젝트의 테스트·린트 명령
│  └─ tasks.yaml     작업 유형별 기본 설정
├─ hooks/            확장점 구현 (프로젝트 전용 파이썬)
├─ knowledge/        AGENTS.md 등 세션에 주입할 프로젝트 지식
└─ runs/             실행 기록 (git에 넣지 않음)
```

### 6.3 upstream 반영 흐름

```
프로젝트에서 문제 발견
   ↓
이 문제가 다른 프로젝트에도 생기는가?
   ├─ 아니오 → hooks/ 에서 해결. 끝.
   └─ 예 → core에 이슈 등록
            ↓
        core에서 수정 + 테스트 추가 + 버전 올림 (1.0 → 1.1)
            ↓
        프로젝트별로 원할 때 pyproject.toml 한 줄 수정
            ↓
        해당 프로젝트의 시험 과제 재실행 → 통과하면 채택
```

핵심은 **"프로젝트가 원할 때" 올린다**는 것이다. fork에서는 원본 수정이 자동으로 반영되지도 않고 안 하기도 어려운데, 패키지에서는 각 프로젝트가 자기 속도로 움직인다.

## 7. 팀과 세션 운영 모델

`Team` 계층은 [중간-7]에서 뺐으므로, **작업 유형(task type)** 중심으로 다시 쓴다.

### 7.1 실행 순서

```
① 요청 접수
   사용자가 목표와 완료 조건을 준다.

② 작업 정의
   MVP: 사람이 직접 작업을 나눈다.
   각 작업에 유형, 의존 작업, 읽기 범위, 쓰기 범위, 검증 명령, 완료 조건.

③ 실행 가능 작업 선택
   의존 작업이 모두 완료 + 쓰기 범위가 실행중인 작업과 겹치지 않음.
   MVP에서는 쓰기 작업을 동시에 하나만 허용한다.

④ 세션 생성
   작업 유형에 따라 sandbox 결정:
     조사·분석 → read_only
     구현·수정 → workspace_write (worktree 안)
     검토      → read_only + 새 스레드
   입력은 작업 계약 + 선행 작업의 산출물 요약. 대화 로그는 넘기지 않는다.

⑤ 결과 수집
   구조화된 결과를 runs/<run_id>/<task_id>/ 에 저장.
   AI의 완료 주장은 기록만 하고 상태를 바꾸지 않는다.

⑥ 결정적 검증  ← 상태를 바꾸는 유일한 지점
   변경 경로가 허용 범위 안인가 (git diff)
   린트·타입 검사 통과
   기존 테스트 통과
   출력 스키마 준수
   전부 통과해야 completed.

⑦ 실패 처리
   1차 실패 → 같은 스레드를 재개하고 실패 내용을 구체적으로 전달 (1회)
   2차 실패 → blocked. 사용자에게 무엇이 왜 실패했는지 보고하고 멈춘다.
   예산 소진 → 즉시 중단.

⑧ 통합
   worktree 변경을 병합. 병합 후 전체 테스트를 한 번 더 돌린다.

⑨ 종료
   Run 상태 확정. 세션 수, 토큰, 시간, 개입 횟수, 재시도 횟수 기록.
```

### 7.2 세션 종류별 판단 기준

| 세션 | 언제 필요한가 | 언제 낭비인가 |
|---|---|---|
| 계획 | 작업이 10개 이상이고 의존 관계가 복잡할 때 | 작업이 5개 이하일 때. 사람이 나누는 게 빠르다 |
| 작업 | 항상 (실제 일을 하는 주체) | — |
| 검토 | 쓰기 작업 후, 자동 검증만으로 판정 못 하는 품질 항목이 있을 때 | 테스트로 완전히 판정되는 작업. 이미 결정적 검증이 답을 준다 |
| 팀장 | **MVP에서는 없음.** 통합 판단이 어려운 사례가 3회 이상 관측된 뒤 검토 | 현재로서는 항상 |

**검토 세션에 대한 보충**: 문헌조사 §9.5의 `Catching One in Five`는 LLM 심판이 사람이 확인한 체계적 문제 9개 중 2개만 잡았고 운영 게이트는 100라운드 중 0건을 표시했다고 보고한다. **검토 세션을 게이트로 쓰지 마라.** 결정적 검증이 게이트이고, 검토 세션은 사람에게 보여줄 참고 의견이다.

## 8. 성능 검증 계획

### 8.1 기준선 3개

| 기준선 | 내용 | 왜 필요한가 |
|---|---|---|
| **B0 (사람 직접)** | 사람이 Codex 한 세션을 직접 붙잡고 끝까지 진행 | 오케스트레이터가 존재할 가치가 있는지 판정 |
| **B1 (단일 세션 자동화)** | 오케스트레이터가 작업을 순차로 세션 1개에 위임, 검증 게이트 적용 | 자동화 자체의 이득 |
| **B2 (병렬)** | 읽기 전용 작업을 동시 2세션 | 병렬화의 이득 |

문헌조사 §14.6이 요구하는 대로 **총 토큰·호출·시간 예산을 함께 기록**해야 한다. 그러지 않으면 "세션이 많아서 좋아진 것"과 "돈을 더 써서 좋아진 것"을 구분할 수 없다.

### 8.2 측정 지표

- 성공률 (사람이 최종 판정)
- **성공 1건당 총 토큰** ← 가장 중요한 비용 지표
- 세션 수, 재시도 횟수
- 벽시계 시간
- **사람 개입 횟수** ← 자동화의 실질 가치
- 중단 후 재개 성공률
- 검증 게이트가 잡은 오류 수 / 게이트를 통과했는데 사람이 발견한 오류 수

마지막 지표가 게이트의 품질을 보여준다. 통과했는데 틀린 게 많으면 게이트가 약한 것이다.

### 8.3 시험 과제

실제 프로젝트에서 뽑되 유형을 섞어야 한다.

1. 순차 의존 구현 과제 (병렬이 불리한 대조군)
2. 독립 조사 과제 3개 (병렬이 유리한 실험군)
3. 실패하는 과제 — 일부러 불가능하거나 모호한 요청 (`blocked` 처리와 보고 품질 확인)
4. 중단 과제 — 실행 중 프로세스를 강제 종료하고 재개 (복구 검증)
5. 권한 위반 과제 — 허용 범위 밖 파일을 고치도록 유도 (게이트가 막는지 확인)

3~5번이 특히 중요하다. **오케스트레이터의 가치는 잘 될 때가 아니라 잘못될 때 드러난다.**

### 8.4 합격·중단 기준

**합격 (B1을 채택할 조건)**
- 성공률이 B0 이상
- 사람 개입 횟수가 B0 대비 50% 이하
- 성공당 총 토큰이 B0의 1.5배 이하
- 5개 시험 과제 유형에서 3·4·5번이 모두 의도대로 동작

**병렬(B2) 채택 조건**
- 벽시계 시간이 B1 대비 30% 이상 단축
- **그러면서** 성공당 총 토큰이 B1의 2배 이하
- 충돌·stale로 인한 재작업이 실행 10회 중 1회 이하

이 조건을 못 맞추면 병렬을 넣지 마라. 문헌조사 §9.0에서 정리한 대로, 예산을 통제하면 다중 세션의 이득은 크게 줄어든다.

**중단 기준 (프로젝트 자체를 재검토할 조건)**
- **2주 안에 B1이 B0을 못 이기면** 오케스트레이터를 계속 만들 이유를 다시 따져라. 이 경우 진짜 필요한 건 오케스트레이터가 아니라 좋은 `AGENTS.md`와 검증 스크립트일 수 있다.
- 검증 게이트를 통과했는데 사람이 오류를 발견하는 비율이 30%를 넘으면, 게이트 설계를 먼저 고쳐야 한다. 세션 구조를 정교하게 만들어도 소용없다.

## 9. 현실적인 MVP

### 9.1 먼저 만들 것

```
1. Run 원장 (SQLite)
   run, task, attempt, session 테이블
   상태 전이는 코드로만. 직접 UPDATE 금지

2. 작업 정의 (YAML, 사람이 작성)
   id, 유형, 의존, 읽기 경로, 쓰기 경로, 검증 명령, 완료 조건

3. Codex 런타임 어댑터
   thread_start / run / resume 를 감싸는 얇은 인터페이스
   sandbox 프리셋 지정

4. 결정적 검증 게이트
   git diff 경로 검사 + 프로젝트 지정 명령 실행 + 종료 코드 판정

5. 재시도 1회 + blocked 보고

6. 중단 후 재개
   프로세스를 죽였다 켜도 원장에서 상태를 복원

7. 사용량 기록
   세션 수, 토큰, 시간을 run 단위로 집계

8. CLI
   run / status / resume / cancel 네 개면 충분
```

이 정도면 **1~2주 분량**이다. 6절 core/project 분리는 이걸 다 만든 뒤 두 번째 프로젝트가 생겼을 때 해도 늦지 않다.

### 9.2 명시적으로 미룰 것

| 미룰 것 | 이유 |
|---|---|
| Team 계층 | [중간-7]. 작업 유형으로 충분하다 |
| 팀장 세션 | [중간-8]. 근거 없음 |
| 계획 세션 | [중간-9]. 사람이 나누는 게 초기엔 낫다 |
| 병렬 쓰기 | [높음-6]. 읽기 전용 병렬부터 |
| fork / 패키지 분리 | [높음-4]. 두 번째 프로젝트가 생긴 뒤 |
| plugin 생태계 | 확장점 설계 비용이 크다. 확장 요구가 실제로 나온 뒤 |
| 웹 대시보드 | CLI + JSON으로 충분하다 |
| 서브에이전트 직접 구현 | Codex가 이미 제공. 필요하면 프롬프트로 호출 |
| worktree 관리 직접 구현 | Codex App에 있음. 확인 후 결정 |

### 9.3 만들기 전에 할 일

**코드보다 먼저 [치명적-1]을 확인하라.** 그다음 반나절만 써서 이걸 해보길 권한다.

> Codex SDK로 스레드를 만들어 `sandbox=read_only`로 "이 저장소에서 X를 찾아라"를 실행하고, 결과를 JSON으로 받아 파이썬에서 파싱한다.

이 30줄이 되면 나머지는 전부 그 위의 배관이다. 안 되면 그 이유가 전체 설계를 바꾼다.

## 10. 최종 판정

### `수정 후 진행`

방향은 옳다. 일반 코드가 상태와 검증을 쥐고 AI에게는 계획·작업·검토만 맡긴다는 핵심 판단은 문헌조사와 Codex 공식 문서가 모두 지지한다. 다만 **배포 방식과 초기 범위는 바꿔야 한다.**

**가장 중요한 이유 세 가지**

1. **전체 fork는 1인 유지보수에서 거의 확실히 실패한다.** 저장소 4개에 같은 수정을 손으로 병합하는 비용은 프로젝트가 늘수록 선형이 아니라 그 이상으로 는다. 그런데 당신이 fork에서 원한 것(프로젝트별 독립 실행, 자유로운 개조, 포함이 아닌 계보)은 **공용 core 패키지 + 프로젝트별 얇은 저장소로 전부 얻을 수 있고**, 거기에 fork가 못 주는 버전 고정까지 따라온다. 목표를 포기하지 않고 비용만 없애는 교환이다.

2. **Codex가 이미 제공하는 것을 다시 만들면 안 된다.** 세션 생성·재개, 세션별 읽기/쓰기 권한, 병렬 서브에이전트, worktree 격리, 훅이 전부 제품에 있다. 당신이 만들어야 할 것은 Codex가 **주지 않는 것** — 크래시를 견디는 상태 원장, 통과 못 하면 완료로 안 넘어가는 결정적 검증 게이트, 예산 상한 — 세 가지뿐이다. 이걸 인식하면 MVP가 몇 달에서 1~2주로 줄어든다.

3. **범용성은 실제 프로젝트 두 개를 겪기 전에는 검증할 수 없다.** 벤치마크로 v1.0을 확정하고 fork하는 순서는, 가장 비싼 시점(이미 분기한 뒤)에 근본 문제가 드러나게 만든다. 실제 프로젝트 하나를 같이 진행하고, 두 번째 프로젝트가 생겼을 때 공통점만 core로 올려라.

## 11. 사용자에게 확인할 질문

결과를 크게 바꾸는 것만 5개로 추렸다.

**1. Codex SDK로 프로그램에서 세션을 돌릴 때, 사용량이 ChatGPT 구독으로 처리되는가 아니면 API 종량제로 청구되는가?** `미확인`

이 프로젝트의 비용 전제 전체가 여기 걸려 있다. 나는 공식 문서에서 확인하지 못했다. [Pricing](https://developers.openai.com/codex/pricing)과 [Authentication](https://developers.openai.com/codex/auth)을 직접 확인하거나, 소액으로 SDK를 몇 번 돌려 사용량이 어느 쪽에서 차감되는지 관찰해보라. **만약 API 과금이라면 세션 수 제약이 지금 계획보다 훨씬 빡빡해지고, 병렬 실행은 사실상 불가능해진다.**

**2. 실제로 적용할 프로젝트가 지금 몇 개이고, 그것들이 얼마나 다른가?**

프로젝트가 당분간 1개라면 범용화 자체를 뒤로 미루는 게 맞다. 2~3개이고 성격이 크게 다르다면(예: EU4 모딩과 웹앱) core에 남길 것이 생각보다 적다는 뜻이고, 그건 core를 더 작게 만들어야 한다는 신호다.

**3. fork를 원한 진짜 이유가 "설정으로는 표현이 안 될 것 같아서"인가, 아니면 "한 저장소에 여러 프로젝트가 섞이는 게 싫어서"인가?**

전자라면 6절 권고안(확장점 + hooks)이 정확히 답이다. 후자라면 저장소 분리만으로 해결되고 fork까지 갈 필요가 없다. **둘 다라면 권고안이 둘 다 만족한다.** 다른 이유가 있다면 알려달라 — 내 권고가 그 이유를 놓쳤을 수 있다.

**4. 오케스트레이터로 실행하려는 작업이 주로 어떤 종류인가?**

조사·분석(읽기 중심)이 대부분이라면 병렬이 유리하고 충돌 문제가 거의 없으므로 설계가 훨씬 단순해진다. 코드 수정(쓰기 중심)이 대부분이라면 병렬 이득은 작고 검증 게이트가 전부다. 지금 설계는 두 경우를 같은 무게로 다루고 있는데, 실제 비중을 알면 MVP를 더 줄일 수 있다.

**5. Codex의 서브에이전트·워크트리·훅 기능을 직접 써본 적이 있는가?**

써봤다면 그 한계가 무엇이었는지가 "직접 만들 것"의 목록을 정한다. 안 써봤다면 **오케스트레이터를 만들기 전에 하루만 써보길 권한다.** 이미 되는 것을 다시 만드는 비용이 이 프로젝트의 가장 큰 위험이다.
