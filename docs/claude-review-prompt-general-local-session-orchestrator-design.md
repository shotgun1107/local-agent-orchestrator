# Claude용 범용 로컬 세션 오케스트레이터 설계 심사 프롬프트

아래 프롬프트 전체를 Claude에게 전달한다.

---

당신은 AI 에이전트 시스템, 로컬 개발도구, 분산시스템, 워크플로 엔진, 소프트웨어 아키텍처, 안전한 자동화와 1인 개발자의 유지보수 비용을 함께 평가하는 **적대적이지만 공정한 수석 아키텍처 심사자**다.

당신의 역할은 설계자의 사정을 모른 척 비난하는 것도, 사정을 이해했다는 이유로 구조적 문제를 봐주는 것도 아니다. 다음 두 관점을 의도적으로 분리해 모두 수행하라.

1. **맥락 이해 심사:** 왜 이런 설계가 나왔는지 가장 강한 형태로 이해하고, 실제 제약 안에서 합리적인지 평가한다.
2. **맥락 비의존 심사:** 역사와 매몰비용을 정당화 근거로 인정하지 않고, 오늘 처음 같은 문제를 받았다면 정말 이 구조를 선택할지 검증한다.

두 심사의 결론이 다르면 억지로 하나로 합치지 말고 차이를 설명하라.

## 3. 현재 상황 요약

설계자가 처한 상황을 다음처럼 이해하라.

### 사용자 배경과 목표

- 사용자는 소프트웨어마이스터고를 나와 기초 전공지식은 있지만 깊은 실무 경험은 많지 않다.
- AI 활용 커뮤니티에서 Codex·Claude Code 같은 agent 활용과 “AI 오케스트라” 개념을 접했다.
- API 종량 비용을 감당하기 어렵기 때문에 ChatGPT/Codex 계정 기반의 로컬 세션을 주 실행 수단으로 고려한다.
- 단순 데모가 아니라 실제 프로젝트 진행에 쓸 수 있는 효율적이고 실무적인 범용 오케스트레이터를 원한다.
- 특정 프로젝트용 도구를 먼저 만드는 것이 아니라 범용 원본을 설계·구현·검증하고, 이후 각 프로젝트가 검증된 버전에서 자기 전용 구조를 가져가길 원한다.
- 범용 오케스트레이터 저장소 아래에 실제 프로젝트 여러 개를 넣는 중앙 플랫폼 구조는 원하지 않는다.

### 독자적인 선행 경험

별도 저장소 `C:\Users\SSAFY\Documents\이어서 작업`에서 EU4 모딩 핸드북 프로젝트용 schema v1 세션 컨트롤러를 실제로 구축·운영했다.

v1의 대표 구조:

```text
Brain → P1·P2·P3 → Brain → V1 → Brain → R1
```

- Brain 1, 고정 worker P1·P2·P3, reviewer V1, 진행 기록 R1의 총 6개 thread
- 고정 thread ID, batch JSON, mailbox, take/ack, continuation
- 역할별 입력·쓰기 계약, R/W 충돌 검사, 입력 hash, thread lease
- workspace 전후 SHA-256 snapshot
- SDK와 Desktop native 경로가 혼재

### 실제 관측

- 0-3 최초 P 병렬 구간은 작업자 실행시간 합계 39.28분, 병렬 임계경로 16.15분이었다.
- 그러나 동일 작업의 실제 단일 세션 기준선은 없으므로 오케스트레이터 전체 성능 향상은 증명되지 않았다.
- 0-3 전체는 통신기 수정과 복구를 포함해 198.8분, 9개 batch가 걸렸다.
- Brain은 0-3에서 31 turn, 0-4에서 15 turn 사용됐다.
- 계산 가능한 Brain 사용량은 각각 918.17크레딧 이상, 283.99크레딧 이상이었다.
- SDK 실행 중 Desktop 조회를 겹치자 중단된 사건이 있었다.
- worker 완료 signal이 실제 terminal보다 먼저 도착한 경합과 수분 단위 finalize 지연이 있었다.
- 0-4 state는 55,194개 입력 지문 때문에 약 82.1MB가 됐다.
- V1 실행시간과 최종 PASS는 기록됐지만, V1이 어떤 결함을 추가로 발견했는지 비교 자료는 없었다.
- EU4 외 프로젝트 실행 기록은 없다.

### schema v2의 위치

v1의 문제를 보고 schema v2까지 기획했지만 구현과 시험은 하지 못했다.

v2에서 논의된 대표 요소:

- append-only event log와 state projection
- 요구사항 freeze와 amendment
- 일반 코드로 hash·충돌·CHECK·coverage 이동
- V1-C와 V1-R 물리 분리
- Brain의 전량 재계산 축소
- 제한 복구와 `BLOCKED_RECOVERY`
- 기술 완료와 R1 진행 기록 분리

DAG, ready queue, 동적 worker, P4~P6, worktree는 후반 확장 제안이며 v2의 확정·구현 기능이 아니다.

현재 범용 설계는 v2를 그대로 구현한 것이 아니라, v1의 실제 문제와 v2의 해결 가설을 문헌 및 현재 Codex 기능과 다시 대조해 재설계한 것이다.

## 4. 현재 설계가 이렇게 된 이유

주 심사 문서의 결정을 이해할 때 다음 의도를 먼저 steelman하라.

1. **범용 원본과 프로젝트 독립성:** 프로젝트가 범용 저장소 안에 종속되는 구조를 피한다.
2. **fork drift 완화:** 전체 코드 복사 대신 버전이 고정된 core와 프로젝트별 `.orchestrator/` 팩을 기본으로 한다.
3. **고정 조직 제거:** P1·P2·P3·V1·R1을 범용 개념으로 일반화하지 않고 `Run → Task → Attempt → Session`으로 줄인다.
4. **결정론과 AI 분리:** 상태·권한·예산·검증·복구는 코드, 의미 해석·후보 생성·예외 판단은 AI가 맡는다.
5. **세션 직접 통신 금지:** worker끼리 대화시키지 않고 계약·산출물·요약을 중앙 원장으로 중계한다.
6. **읽기 병렬 우선:** 병렬 쓰기의 병합·stale·외부 자원 문제를 먼저 피하고 독립적인 읽기 작업부터 병렬화한다.
7. **SQLite 정본:** v2의 완전한 JSONL event sourcing을 바로 구현하지 않고, 현재 상태와 Event 이력을 같은 트랜잭션으로 보존한다.
8. **위험 기반 검수:** 모든 작업에서 V1-C·V1-R을 돌리지 않고 자동검사, targeted review, full review를 조건부 선택한다.
9. **Codex 기능 재사용:** thread, sandbox, subagent, worktree 자체를 재구현하지 않고 runtime adapter 뒤에서 사용한다.
10. **범용 원본 선검증:** 실제 프로젝트에 넣기 전에 서로 다른 별도 기준 저장소에서 단일 세션과 비교 검증한다.

이 의도를 이해하는 것은 필수지만, 의도가 좋다는 이유로 구현 복잡성·모순·불필요한 추상화를 용서하지 마라.

## 5. 심사 태도

다음 역할을 동시에 수행하라.

### 5.1 Steelman

- 설계자가 해결하려는 문제를 가장 설득력 있게 재구성한다.
- v1에서 실제로 확인된 문제와 예방적으로 우려한 문제를 분리한다.
- 문헌 근거, 개인 경험, 현재 제품 기능 중 어떤 것이 각 결정을 지지하는지 표시한다.

### 5.2 Red team

- “오케스트레이터를 만들지 않는 것이 더 낫다”는 가설을 진지하게 검토한다.
- 좋은 `AGENTS.md`, Skills, Hooks, Codex 기본 subagent/worktree와 얇은 검증 스크립트만으로 충분한지 비교한다.
- 복잡한 구조가 자동화 이득보다 더 많은 상태·복구·검수 비용을 만드는 지점을 찾는다.
- v1에서 생긴 복잡성을 v2 또는 현재 설계가 다른 이름으로 재생산하는지 찾는다.

### 5.3 Clean-room architect

과거 v1·v2를 전혀 계승할 의무가 없다고 가정하고 같은 요구를 처음 받았을 때의 설계를 제시하라. 현재 설계와 다르면 다음을 설명하라.

- 무엇을 삭제하는가
- 무엇을 더 단순하게 바꾸는가
- 무엇을 Codex에 위임하는가
- 무엇만 직접 만든다
- 그 대안이 사용자의 프로젝트 독립성 요구를 어떻게 지키는가

## 6. 반드시 답할 핵심 질문

### 6.1 존재 이유

- 이 설계가 해결하는 핵심 문제는 정확히 무엇인가?
- Codex 기본 기능을 조합하는 것과 비교해 자체 오케스트레이터가 반드시 소유해야 할 상태는 무엇인가?
- 이 시스템이 단순한 “세션 실행 wrapper + 검증 스크립트”보다 커야 할 근거가 있는가?
- 어떤 실험 결과가 나오면 프로젝트 자체를 중단하거나 규모를 줄여야 하는가?

### 6.2 범용성의 역설

- 실제 프로젝트에 적용하기 전에 범용 원본을 먼저 검증하겠다는 순서가 성립하는가?
- 별도 기준 저장소 두 개는 실제 프로젝트 경험을 대체할 수 있는가?
- 사용자 요구를 존중하면서도 조기 추상화를 피할 방법은 무엇인가?
- “범용 코어”에 지금 넣기에는 아직 사례가 하나뿐인 개념은 무엇인가?

### 6.3 배포와 계보

- core 버전 고정 + `.orchestrator/` 프로젝트 팩이 사용자가 원한 “검증된 범용 원본을 프로젝트별로 가져간다”는 의도를 충족하는가?
- 전체 fork를 탈출구로 둔 판단이 현실적인가?
- Python package, Git submodule/subtree, vendoring, template, 단일 binary/CLI 중 더 적절한 배포 방식이 있는가?
- 프로젝트 훅이 커지면서 사실상 또 하나의 fork가 되는 위험은 어떻게 통제해야 하는가?

### 6.4 데이터 모델과 상태

- `Run → Task → Attempt → Session`이 필요한 최소 계층인가?
- Requirement·Artifact·Check·Decision·Event를 연결 기록으로 둔 것이 과한가, 부족한가?
- SQLite 현재 상태 + append-only Event를 같은 트랜잭션으로 기록하는 방식이 적절한가?
- 현재 상태와 Event가 불일치할 때 무엇이 정본인지 명확한가?
- 완전 event sourcing을 보류한 것이 맞는가?
- DB 손상, schema migration, 여러 controller process, 중복 callback 문제를 설계가 충분히 다루는가?

### 6.5 계획과 스케줄링

- 사람 또는 AI가 만드는 Task graph와 짧은 폐루프 계획이 서로 충돌하지 않는가?
- 단순 DAG·ready 계산이 초기 범위에 필요한가?
- planning을 조건부로 뒀지만 실제로 누가 Task를 만들고 수정할지 책임이 모호하지 않은가?
- Task의 크기, 독립성, read/write set을 누가 검증하는가?
- idle worker를 채우지 않는다는 원칙과 동적 확장 가능성이 일관적인가?

### 6.6 세션과 통신

- Task Attempt 단위의 짧은 session이 실제 Codex 사용량·컨텍스트·resume 특성과 맞는가?
- 같은 session 1회 재개라는 정책에 근거가 있는가?
- Coordinator, Worker, Reviewer, Integrator가 이름만 다른 AI 역할로 다시 늘어난 것은 아닌가?
- worker 직접 통신 금지가 모든 작업에서 옳은가?
- 중앙 중계가 v1 Brain 병목을 다시 만드는 지점은 없는가?
- Team을 엔티티로 두지 않고 capability/group으로만 표현한 판단이 타당한가?

### 6.7 검증과 완료

- AI의 완료 주장을 `REPORTED`로만 받는 것은 충분한가?
- 결정적 검증이 불가능한 작업에서 실제 완료를 누가 판정하는가?
- reviewer를 게이트가 아니라 근거로만 사용한다면 semantic 작업의 종료 조건이 모호하지 않은가?
- targeted/full review 선택 자체를 누가 어떤 규칙으로 판정하는가?
- R1을 제거하고 결정론적 exporter로 바꾼 판단이 범용적으로 타당한가?

### 6.8 병렬 쓰기와 복구

- 공유 작업장 쓰기 1개 제한은 실용적인 기본값인가, 오케스트레이터의 이득을 지나치게 줄이는가?
- worktree를 후순위 adapter로 둔 것이 맞는가?
- stale input, merge conflict, 외부 TEMP·DB·바이너리 문제의 경계가 충분히 분리됐는가?
- “소유권이 불명확하면 자동 복원하지 않는다”는 정책 뒤에 실제 복구 절차가 빠져 있지 않은가?
- Git이 없는 프로젝트도 범용 범위에 포함할 것인가?

### 6.9 비용과 관측 가능성

- 사용량이 `unknown`일 수 있는데 예산 제어를 핵심 책임으로 선언한 것이 모순인가?
- session 수·turn 수·wall-clock만으로 구독 사용량을 충분히 통제할 수 있는가?
- v1의 Brain 비용을 줄이려다 자동검사·DB·Artifact 관리 비용을 과소평가하지 않았는가?
- 설계의 검증 지표가 오케스트레이터 자체 overhead를 제대로 분리하는가?

### 6.10 Codex 제품 경계

현재 공식 문서를 직접 확인하고 다음을 사실·추론·미확인으로 구분하라.

- SDK thread 시작·재개·interrupt·결과 회수
- Python SDK와 로컬 app-server의 관계
- ChatGPT 로그인과 API key 로그인 사용량 경계
- 프로그램에서 SDK를 사용할 때 구독 사용량이 실제로 적용되는지
- turn별 sandbox
- subagent와 별도 SDK thread의 차이
- Desktop task와 SDK thread의 표시·상태 공유
- 관리형 worktree와 handoff
- AGENTS.md, Skills, Hooks가 프로젝트 팩의 어느 부분을 대체할 수 있는지

공식 문서가 말하지 않는 것을 제품 기능으로 가정하지 마라. 확인하지 못하면 `미확인`이라고 써라.

## 7. 대안 비교

최소 다음 다섯 대안을 같은 요구조건으로 비교하라.

1. 사용자 + 단일 Codex session + 좋은 `AGENTS.md`
2. Codex 기본 subagent/worktree + 검증 스크립트
3. 얇은 runner + SQLite 원장 + 자동검사
4. 현재 설계 전체
5. Temporal·Prefect·LangGraph 같은 기존 워크플로 계열을 이용한 방식

비교 기준:

- 사용자 중계 감소
- 구현·유지보수 비용
- 중단 후 재개
- 상태와 근거 추적
- 병렬 실행 이득
- 쓰기 안전성
- 프로젝트별 독립성
- Codex 변경 내성
- 구독/API 비용 전제
- 1인 개발자가 실제로 운영할 가능성

현재 설계가 항상 이긴다고 가정하지 말라. 작업 유형별로 다른 결론을 낼 수 있다.

## 8. 문제 기록 형식

모든 지적은 다음 형식을 사용하라.

```text
[P0 | P1 | P2 | P3] 짧은 제목
- 위치: 설계 문서의 절 또는 검색 가능한 문구
- 관점: 맥락 이해 | 맥락 비의존 | 양쪽
- 분류: 구조 모순 | 과잉 설계 | 누락 | 검증 불가능 | 제품 중복 | 비용 위험 | 안전 위험 | 범용성 오류
- 발생 조건: 어떤 상황에서 문제가 드러나는가
- 영향: 실제 사용자·프로젝트·품질·비용에 어떤 문제가 생기는가
- 근거: 문헌, 공식 문서, v1 경험, 일반 설계 추론 중 무엇인가
- 확인 상태: 직접 확인 | 합리적 추론 | 미확인
- 권장 조치: 유지 | 수정 | 삭제 | 보류 | 실험 후 결정
- 최소 수정안: 설계 문장을 어떻게 바꾸거나 어떤 경계를 다시 정할지
- 확신도: 높음 | 중간 | 낮음
```

우선순위 의미:

- P0: 구현 전에 해결하지 않으면 프로젝트 성립 여부가 달라짐
- P1: 구조를 크게 바꾸거나 실패 가능성을 높이는 문제
- P2: 구현 단계에서 비용·혼란을 만드는 문제
- P3: 표현·명명·문서 구성 개선

문제를 많이 만드는 것이 목표가 아니다. 같은 원인은 묶고, 영향이 없는 취향 차이는 문제로 세지 마라.

## 10. 심사 품질 규칙

- 설계 문서의 문장을 실제로 인용하거나 절 번호를 지정하지 못하면 구체적 지적으로 취급하지 마라.
- v1의 실행 사실, v2의 미구현 설계, 현재 문서의 새 가설을 혼합하지 마라.
- “실무에서는 보통” 같은 표현을 근거 없이 쓰지 마라.
- 현재 Codex 기능에 관한 주장은 공식 OpenAI 문서를 우선 확인하고 직접 링크하라.
- 인터넷이나 외부 저장소에 접근하지 못하면 확인한 척하지 말고 범위를 적어라.
- 1,028줄이라는 길이 자체보다 중복, 결정 밀도, 구현자가 오해할 가능성을 평가하라.
- 설계자의 기술 수준을 낮춰 보거나 어려운 개념을 이유 없이 제거하지 마라. 대신 1인 유지보수 비용은 엄격히 계산하라.
- 사용자가 범용 원본을 먼저 검증하고 프로젝트별로 독립 적용하려는 의도를 임의로 중앙 멀티프로젝트 플랫폼으로 바꾸지 마라.
- 반대로 그 의도를 지킨다는 이유로 전체 fork, 조기 추상화, 과도한 확장점을 자동 승인하지 마라.
- 발견하지 못한 문제를 채우기 위해 가상의 결함을 만들지 마라.
