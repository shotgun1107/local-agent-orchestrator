# 연구 운영 결정 기록

## 2026-09-16 — 연구 관리와 실행 공간 분리

- 사용자 의도: 상용 서비스 개발보다 연구 기획·실험·검증의 연속성에 집중한다.
- Documents의 기존 문서 폴더는 총괄·운영의 기준 공간으로 유지한다. 이동 안내만 남기는 이전 구조를 대체한다.
- LAO는 코드 작성, 실행, 검토, 실험 및 환경을 모으는 공간이다.
- 순환: 연구 질문·계획 → LAO 작업 → 근거·결과 보고 → 문서 폴더에서 해석·다음 방향 결정.

## 2026-09-16 — 하나의 Git 저장소로 공동 이력 관리

- 기존 `local-agent-orchestrator`, `origin/codex/phase-d-artifacts`를 유지한다.
- 관리 문서의 실제 편집 공간과 Git 전달본을 구분한다. 관리 폴더 자체는 Git 저장소가 아니다.
- 고정 허용 목록과 이전 일치 해시로 `collect`/`refresh`한다. 양쪽 수정, 삭제, 경로 변경은 자동 해결하지 않는다.
- 별도 원격 저장소·공유 링크·중복 clone·Git 이력 재작성은 만들지 않는다.
- 새 PC는 코드를 수신하고 환경은 명세로 재구성한다. 설치된 venv·인증·Docker image를 Git에 넣지 않는다.
- 과거 원본 보존과 새로운 실행 준비는 별개다. 역사적 state·seal·절대경로를 새 환경에 맞춰 고치지 않는다.

이 결정은 운영 구조에 대한 것이다. 후속 연구 가설, 실험 대상, 새 experiment나 모델 사용 승인을 포함하지 않는다.

## 2026-09-16 — 감사의 F8·F9·F3부터 교정

- 감사 설명 후 사용자가 제안 순서의 진행을 승인했다. 실제 실행 설정·필수 입력·완료 증거의 연결을 먼저 고친다.
- 사용자 일시 정지 요청을 따랐고 재개 지시 뒤 나머지 경계·회귀 검증을 수행했다.
- 과거 PASSED에 새 증거를 소급 추가하거나 자동 재실행하지 않는다. 증거가 없거나 달라진 복구는 BLOCKED로 둔다.
- 이번 승인은 세 코드 경계와 model-free 검증·기록에 한정한다. F5 등 잔여 감사와 새 연구/실험은 분리한다.

## 2026-09-16 — 후속 F5 공개 Schema 교정

- 사용자가 다음 후보 F5의 진행을 별도로 승인했다.
- Python 실행 의미를 되돌리거나 Schema 제한을 임의 완화하지 않고 기존 생성기로 현행 계약을 반영한다.
- 실제 export 소비자와 별도 설치한 새 QA wheel을 확인한다. 기존 venv·과거 wheel·candidate·봉인 자료는 교체하지 않는다.
- 이번 승인은 F5와 model-free 검증·기록까지다. Live 또는 다음 감사 항목의 자동 실행 승인이 아니다.

## 2026-09-16 — 후속 F10 실행 중 취소 교정

- 사용자가 다음 후보 F10의 진행을 승인했다. 단일 controller 잠금을 제거하지 않고 별도 Run별 취소 요청을 전달한다.
- 요청 접수와 중단 완료를 분리한다. interrupt ACK만으로 종료를 확정하지 않으며 미확인은 격리·BLOCKED로 남긴다.
- 동결 migration·상태 전이표와 과거 원본은 유지한다. 요청의 새 backup 보존과 취소 보고서 일치는 F10의 내구적 제어 경계에 포함한다.
- F11/F12 전체 교정, 실제 모델·새 experiment·Live는 이번 승인에 포함하지 않는다.

## 2026-09-16 — 후속 F11 삭제·rename 관측 교정

- 사용자가 F11 진행을 승인했다. 삭제를 자동 복원하지 않고 실제 변경으로 관측해 범위·입력·Check 관문에 전달한다.
- 안정된 부재만 삭제로 취급하며 권한/IO 오류·관측 중 변동을 숨기지 않는다. 필수 입력·선언 Artifact 존재 계약은 유지한다.
- controller 계약 검토 중 직전 F10의 TIMED_OUT 분기 누락을 발견해 사용자에게 알리고, 직접 재현과 작은 보정·회귀를 함께 진행했다.
- F12와 나머지 비교 결함은 별도다. 실제 모델·새 experiment·Live 승인은 포함하지 않는다.

## 2026-09-17 — 후속 F12 backup 검증 교정

- 사용자가 F12 진행을 승인했다. 기존 schema-1 생성 형식을 검사하고 불완전한 묶음을 거부한다. 원본 DB·backup을 migration/복원하지 않는다.
- 해시를 확인한 DB bytes의 메모리 검사, manifest/실제 payload/Run 소유의 교차 검증과 외부 expected Run ID 대조를 적용한다.
- 검증 성공을 생성자 진위·최신성·전체 DB의 다른 Run payload·실제 실행 준비로 확대하지 않는다. 외부 seal과 Live 두 턴 관문은 유지한다.
- 중간 timeout 시간 실패는 실패대로 기록하며 기대 시간을 완화하거나 원인 해결을 선언하지 않는다.
- F1/F2/F4/F6/F14, 새로운 연구·experiment·실제 모델 사용은 이번 작업 범위 밖이다.

## 2026-09-17 — 잔여 감사의 연속 교정 승인

- 사용자가 남은 감사 항목은 하나씩 재확인하지 않고 계속 수정하도록 승인했다. 기존 결함의 코드·model-free 검증·기록·통상 Git 전송을 진행한다.
- F1/F2/F4/F6을 교정했다. mixed 원장 제약은 DDL을 바꾸지 않고 종료 stage/Check 증거에 원인을 보존한다.
- F14는 역사 v1 봉인을 보존하면서 새 실행/승격을 차단하고 별도 v2 행동 oracle/source bundle을 구현한다.
- 단위시험으로 실제 isolation을 주장하지 않는다. 실제 격리 qualification까지 F14는 investigating이다.
- 새 experiment·실제 모델/SDK/Judge workload 승인 관문은 유지한다. 중간 실패를 기록하며 이전 timeout 변동 해결도 주장하지 않는다.

## 2026-09-17 — F14 기준 코드 진단 연결과 NO-GO

- 사용자가 검증기 연결·입력/환경 고정·사전점검의 진행을 승인했다. 실제 workload와 새 비교 experiment 승인은 아니다.
- 동일 Python 프로세스에서 후보와 oracle가 실행되는 구조적 한계를 확인했다. Container만으로 판정 신뢰가 확보됐다고 주장하지 않는다.
- 기존 v1 차단을 유지하고 검토된 reference만 받는 별도 진단 경로로 연결했다. 모든 출력의 comparison_authorized/challenge_ready는 false다.
- 관련 model-free 146개 통과와 실제 Docker engine 연결 불가를 분리해서 보고한다. engine 시작·이미지 설치·로그인·실제 실행은 하지 않는다.
- F14 전체 해결 전에는 oracle 신뢰 경계와 실제 격리 qualification이 필요하다. 회사 진단도 Environment Closure GO 뒤 별도 실행 승인 턴을 요구한다.

## 2026-09-29 — 잔여 구현 재개와 v3 외부 판정

- 사용자가 남은 구현을 자율적으로 진행하도록 요청했다. 새 연구·병렬 B2/B3로 범위를 넓히지 않고 잔여 F14부터 구현한다.
- 판정기는 호스트, 후보/공개 관측 adapter는 read-only·무네트워크 컨테이너로 분리한다. 후보의 합격 선언을 신뢰하지 않는다.
- 설치된 Docker Desktop을 시작해 사전검증한다. 설치/업데이트/pull·로그인·과거 state 변경은 하지 않는다.
- 기존 부분 fixture가 빠진 runner dependency를 요구하므로 기존 4개 공통 유틸리티와 동일한 지원 모듈을 명시적으로 제공한다. 평가 대상 함수는 대체하지 않는다.
- Fake GO는 native 실행 근거로 거부한다. 실제 qualification과 모델 실행의 별도 턴 관문은 유지한다.

## 2026-09-29 — 실제 연구 이전 준비 작업의 연속 진행 지시

- reference 환경 GO 보고 뒤 사용자가 명시적 중단·종료 지시 전까지 준비 작업을 계속하라고 지시했다.
- 이번 세션의 고정 9종 model-free 진단·교정·회귀·기록은 매 항목마다 재승인을 묻지 않는다.
  일반 Live 정책 전역 변경이나 새 연구/Phase F Cell/SDK·model/B2·B3 승인은 아니다.
- 각 진단의 clean source/plan·exact 환경·native no-op·600초 receipt·1회 표식은 그대로 검증한다.
  예상 밖 실패는 보존하고 원인을 확인한다. 같은 root 재실행·성공 재분류는 하지 않는다.
- 최초 native reference 11개 그룹/10 property는 통과했다. 후속 9종 진단과 한계는
  `docs/operations/audit-f14-native-qualification-20260929.md`에 기록한다.
- 후속 고정 9종은 정상 2종 합격/오류 7종 거부와 증거 재검증까지 완료했다. 이 결과로
  일반 Worker 평가·정교한 전체 관측 위조·실제 OS/SDK 검증까지 해결됐다고 선언하지 않는다.
  실제 연구/모델/Phase F 작업은 시작하지 않고 새 세션이 읽을 인수인계를 정리한다.

## 2026-09-29 — 감사·유지보수 공식 종료까지 연속 진행

- 사용자는 고정 준비 진단에서 멈추지 말고 프로젝트의 감사·유지보수를 공식 종료하여
  실제 기능개발을 이어가기 직전까지 자율 진행하라고 명시했다. 목표를 작은 부분 통과로 대체하지 않는다.
- 원래 F1~F14와 새 직접 재현 결함, 배포·복원·이력·문서의 검증 공백을 항목별 현재 근거로 닫는다.
  완료를 증명하지 못한 항목은 OPEN으로 유지하고 다음 가능한 교정을 진행한다.
- 확인한 controller deadline 후속 결함은 유지보수 범위에 포함한다. 과거 실패 원본은 보존한다.
- 새 기능/B2/B3/연구 experiment/실제 model·SDK turn/Phase F Cell은 시작하지 않는다.
  실제 모델 사용을 포함하지 않는 기존 감사 교정·회귀·기록·일반 Git 전달을 이어간다.
