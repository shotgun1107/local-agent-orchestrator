# 다음에 이어서 할 작업

현재 상태는 `STATUS.md`, 문서 읽기 우선순위는 연결된 저장소의 `docs/README.md#session-start`를 따른다.
여기는 **현재 작업과 다음 범위만** 기록한다. 과거 회차의 미완료·대기·실행 지시는 결과 보고서와 Git 이력에 보존한다.

## 직전 작업 완료 — 실제 새 에이전트 인수 확인과 안내 교정

- Runner 입구·인덱스·인수인계·과거 재개 프롬프트와 오래된 incident의 후속 안내를 교정했다.
- 이전 대화·기대 답 없이 파일만 읽은 새 에이전트 1명이 사용 코드/보존본, 완료/미확인, 다음 범위/금지 영역을 구분했다.
- 인수 중 찾은 policy v1의 현재형 안내와 benchmarks 역사 표지를 교정하고, v4의 v2/v3 공통 의존성을 설명했다.
  같은 에이전트의 수정 후 대조도 통과했다. 이는 별개의 새 블라인드 시험이나 모든 AI의 이해 보증은 아니다.
- 문서 15개·관리 18개·기록 10개와 관련 model-free 정책 104개가 통과했다. 기존 종료 보고서의 `blind-handoff-check` 절에 근거가 있다.
- 과거 state/raw/seal·제품 실행 코드·실험 결과는 바꾸지 않았다. 프로젝트 모델·실제 SDK·Docker workload는 수행하지 않았다.
- 확인된 인수 안내 문제는 교정 완료다. 전송 commit·미전송 로컬 자료는 기존 SYNC:AUTO에서 확인한다.

## 이후 기능개발·연구 범위

1. 감사 수선은 2026-09-30 종료했다. 사용자가 다음 기능개발 또는 연구 질문을 지정하면 그 명세·완료 조건부터 작업한다.
   B2/B3·새 비교 experiment·외부 pilot을 임의로 선택하지 않는다.
2. 완료한 reference·matrix-1/3, 중단 matrix-2와 과거 pair는 다시 실행하지 않는다.
   저장 증거 확인은 해당 보고서의 외부 SHA와 정확한 verifier로 읽기 전용 재검증한다.
3. 실제 모델/SDK/Phase F가 필요한 새 작업은 별도 candidate와 Environment Closure/실행 승인 관문을 밟는다.
   감사 종료나 v4 21종 통과를 실제 OS/SDK 보안·인증·다른 PC 준비·정식 비교 승인으로 해석하지 않는다.

## 새 세션의 첫 작업

1. 실제 LAO/repo와 적용 AGENTS.md를 확인하고, 관리 문서 status·로컬 변경을 먼저 검사한다.
2. `docs/README.md#session-start`의 순서로 현재 상태·다음 범위·기존 SYNC:AUTO를 인수한다.
3. 코드 작업 전에 개발 환경에 진입해 `tools/workspace/check_environment.py`를 실행한다.
   과거 설치 wheel 대신 현재 소스를 사용하는지 확인한다. 단순 문서 열람만으로 환경 설치나 Live 점검을 시작하지 않는다.
4. 이미 승인된 비라이브 작업은 그 범위에서 진행한다. 맥락 확인 자체를 추가 승인 관문으로 만들지 않는다.
   사용자 범위가 비어 있으면 새 개발 목표를 추측하지 않는다.

## PC 전환이 요청된 경우

- 기존 변경 보존 → 원격 commit 고정·수신 → 기존 SYNC:AUTO 확인 → 관리 사본 refresh → 개발 환경 점검 순서다.
- 양쪽 관리 문서가 다르면 먼저 충돌을 보존한다. 받는 PC에 필요한 venv는 복원 계약으로 새로 만들며 설치 범위 승인을 따른다.
- 필요한 외부 원문·이미지는 지정된 범위만 별도 무결성 검증·전달한다. Git 수신만으로 전체 환경 준비 완료라고 하지 않는다.
- 보조 worktree 자료는 소유 작업과 비교해 별도로 결정한다. 자동 stage·삭제·prune하지 않는다.
