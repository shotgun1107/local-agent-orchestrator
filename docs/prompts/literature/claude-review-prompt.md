# Claude용 AI 오케스트레이션 문헌조사 평가 프롬프트

아래 프롬프트 전체를 Claude에게 전달한다.

---

당신은 AI 에이전트 시스템, 분산시스템, 자동계획, 제어이론, 조직과학, 집단지성 및 기술 문헌조사 방법론을 폭넓게 이해하는 **비판적 동료 심사자(peer reviewer)**다.

현재 프로젝트 폴더에 있는 다음 문서를 평가하라.

- 주 평가 대상: `docs/research/ai-orchestration-broad-literature-review.md`
- 비교·범위 확인용 보조 문서: `docs/research/ai-orchestration-practical-cases-and-methods.md`

## 평가 목적

주 문서가 AI 오케스트레이션을 특정 LLM 프레임워크에 한정하지 않고, 고전 분산 AI부터 최신 다중 에이전트 연구와 인접 분야까지 정확하고 유용하게 종합했는지 평가하는 것이 목적이다.

이 문서는 의도적으로 **‘간단한 오케스트라에 권장하는 최소 구조’는 다루지 않으며**, 실제 사례와 구체적인 구축 방법은 보조 문서에 분리돼 있다. 따라서 최소 구현 구조가 없다는 이유로 감점하지 말라. 대신 문헌조사 문서로서의 범위, 정확성, 근거, 종합 수준을 평가하라.

## 작업 원칙

1. 평가 전에 주 문서를 처음부터 끝까지 읽어라. 제목이나 초록만 보고 판단하지 말라.
2. 보조 문서는 주 문서와의 불필요한 중복, 역할 분리, 상호 참조가 적절한지 판단할 정도로 확인하라.
3. 칭찬 위주의 일반적인 감상평을 쓰지 말라. 잘된 부분도 구체적 근거가 있을 때만 인정하라.
4. 문서에 쓰인 주장과 출처가 실제로 대응하는지 검사하라.
5. 인터넷 접근이 가능하면 중요한 출처와 최신 표준을 직접 확인하라. 특히 다음을 우선 검증하라.
   - 수치가 인용된 실험 결과
   - 2025~2026년 논문과 사전출판물
   - MCP 2026-07-28, A2A v1.0, OpenTelemetry GenAI 의미 규약
   - NIST AI Agent Standards Initiative
   - 논문의 발표 상태가 동료평가인지 사전출판인지에 대한 표시
6. 인터넷에 접근할 수 없거나 원문을 확인하지 못한 항목은 추측해서 판정하지 말고 `검증 불가`라고 표시하라.
7. 저자의 해석과 원문이 직접 주장한 내용을 구분하라. 인접 분야의 개념을 AI 오케스트레이션에 옮긴 부분은 사실 주장인지, 설계적 유추인지 표시하라.
8. 최신 논문이라는 이유만으로 강한 근거로 취급하지 말라. 발표 장소, 동료평가 여부, 실험 규모, 재현성, 적용 범위를 함께 보라.
9. 출처 수보다 출처의 품질과 주장-근거 대응을 평가하라.
10. 원문 파일은 수정하지 말라. 평가는 별도 파일에 저장하라.

## 반드시 검토할 항목

### 1. 정의와 범위

- 문서가 제안한 AI 오케스트레이션의 작동 정의가 지나치게 넓거나 모호하지 않은가?
- 모델 라우팅, 추론, 도구, 워크플로, 다중 에이전트, 자원, 거버넌스 층의 구분이 유용하고 일관적인가?
- ‘에이전트’, ‘워크플로’, ‘오케스트레이터’, ‘프로토콜’, ‘거버넌스’의 구분이 학술·실무 문맥에서 타당한가?
- 제목이 약속한 ‘폭넓은 문헌조사’에 실제 내용이 부합하는가?

### 2. 역사적 계보의 정확성

다음 분야가 단순한 비유가 아니라 정확하게 설명되고 현대 AI 오케스트레이션과 적절히 연결됐는지 검토하라.

- Contract Net Protocol
- Blackboard architecture
- Actor model
- BDI agents
- Brooks의 subsumption/reactive architecture
- 인지 아키텍처와 CoALA

잘못된 계보 연결, 시대착오적 해석, 원문보다 과장된 주장이 있으면 지적하라.

### 3. 최신 LLM 에이전트 문헌

다음 연구의 핵심 설명이 정확한지 확인하라.

- ReAct
- Toolformer
- Tree of Thoughts
- Reflexion
- AutoGen
- MetaGPT와 ChatDev
- Mixture-of-Agents
- Magentic-One

각 연구의 실험 결과를 일반적인 생산 환경의 사실처럼 확대 해석한 부분이 있는지 확인하라.

### 4. 다중 에이전트의 실증 근거

다음 주장과 수치를 특별히 엄격하게 검증하라.

- SILO-BENCH의 실험 규모와 대규모 조정 실패
- MAS-BENCH의 공유 상태·규약·종료 실패
- 통신 토폴로지 연구의 희소 그래프 관련 결론
- Google의 agent scaling 연구에서 보고한 개선·악화·오류 증폭 수치
- `Measuring Agents in Production`의 20개 사례, 86명 실무자, 26개 도메인 및 비율
- LLM 군집의 상관 오류와 유효 표본 크기 1.2~1.3 주장

수치가 맞더라도 적용 범위나 전제가 본문에서 충분히 제한됐는지 판단하라.

### 5. 인접 분야의 전이 가능성

다음 분야에서 가져온 개념이 실제 설계 통찰인지, 표면적 비유인지 구분하라.

- 이벤트 소싱, 내구성 실행, Saga, reconciliation loop
- HTN planning과 스케줄링
- Model Predictive Control
- 다중 로봇 작업 할당과 시장 기반 조정
- NASA Remote Agent
- 트랜잭티브 메모리
- Incident Command System의 span of control
- 집단지성, 독립성, 상관 오류

각 연결에 대해 다음 중 하나로 판정하라.

- `직접 전이 가능`: 메커니즘과 실패 조건이 충분히 대응함
- `조건부 전이 가능`: 유용하지만 중요한 전제가 다름
- `설명적 비유`: 사고를 돕지만 설계 근거로 쓰기에는 약함
- `부적절한 연결`: 원 분야의 의미를 왜곡하거나 근거가 없음

### 6. 보안·표준·최신성

- MCP와 A2A의 책임 경계 설명이 정확한가?
- OpenTelemetry GenAI 규약의 상태와 버전 변동성이 올바르게 표현됐는가?
- NIST 자료를 강제 표준처럼 오해하게 쓰지 않았는가?
- 간접 프롬프트 주입, 최소 권한, 위임 사슬, 감사 가능성에 관한 결론이 근거와 부합하는가?
- 조사 기준일 `2026-08-03` 현재 폐기되거나 변경된 링크·버전·상태가 있는가?

### 7. 종합 결론의 타당성

문서가 제시한 12개 설계 법칙 각각을 다음 기준으로 평가하라.

- 여러 문헌에서 실제로 반복 지지되는가?
- 저자의 합리적 종합이지만 직접 근거는 제한적인가?
- 예외 조건 또는 반례가 누락됐는가?
- 실무 설계 규칙으로 쓰기에 표현이 지나치게 강한가?

각 법칙에 대해 `강하게 지지`, `조건부 지지`, `근거 부족`, `수정 필요` 중 하나로 판정하고 한두 문장으로 이유를 써라.

### 8. 누락과 편향

다음과 같은 누락 가능성을 적극적으로 찾아라.

- 중요한 반대 결과 또는 다중 에이전트가 유리한 강한 실증 연구
- 메커니즘 설계, 메모리, 계획, 통신, 평가의 핵심 문헌
- 경제학의 메커니즘 디자인·조직 설계·게임이론
- 분산 합의, CRDT, event-driven architecture, 데이터 계보
- 인간공학, 자동화 편향, 고신뢰 조직, 안전공학
- 운영연구의 큐잉·스케줄링·제약 최적화
- 모델 라우팅·캐스케이드·예산 기반 추론
- 에이전트 신원, 인증, 책임 추적
- 비영어권 또는 특정 기업 연구에 대한 편향

모든 분야를 추가하라고 기계적으로 요구하지 말고, 문서의 핵심 논지를 실제로 강화하거나 반박할 수 있는 누락만 우선 제안하라.

### 9. 문서 품질

- 같은 주장이 지나치게 반복되는가?
- 사실, 해석, 권고가 명확히 구분되는가?
- 표와 도식이 정보를 실제로 압축하는가?
- 1,000줄 이상의 길이가 내용 밀도에 비해 정당한가?
- 다른 AI나 개발자가 나중에 읽고 재사용하기 쉬운가?
- 참고문헌이 정식 서지 형식이 아니라 링크 중심인 점이 어떤 문제를 만드는가?
- 내부 링크와 외부 링크가 정확한가?

## 채점표

각 항목을 10점 만점으로 채점하고 반드시 근거를 제시하라.

| 항목 | 배점 |
|---|---:|
| 범위와 문제 설정 | 10 |
| 개념·역사적 정확성 | 10 |
| 최신 문헌의 정확성 | 10 |
| 주장과 출처의 대응 | 10 |
| 근거 수준 구분 | 10 |
| 분야 간 종합의 깊이 | 10 |
| 반례·한계·불확실성 처리 | 10 |
| 실무·연구 활용성 | 10 |
| 구성·가독성·중복 관리 | 10 |
| 최신성·유지보수 가능성 | 10 |

총점은 100점이지만, 숫자만 주지 말고 **왜 그 점수인지 재현 가능한 근거**를 적어라.

## 문제점 기록 형식

발견한 문제는 중요도순으로 정리하라. 각 항목에 다음 필드를 사용하라.

```text
[Critical | Major | Minor] 짧은 제목
- 위치: 문서의 장·절 또는 검색 가능한 문구
- 현재 주장: 문제가 되는 내용을 짧게 요약
- 판정: 사실 오류 | 출처 불일치 | 과도한 일반화 | 근거 부족 | 오래된 정보 | 모호한 표현 | 구조 문제
- 이유: 왜 문제인지
- 확인 근거: 검증한 원문이나 공식 자료 링크
- 권장 수정: 교체하거나 보완할 문장 또는 구체적 수정 방향
- 확신도: 높음 | 중간 | 낮음
```

문제가 없는 항목을 억지로 만들지 말고, 동일 원인에서 나온 문제는 묶어라.

## 최종 출력 구조

다음 순서를 반드시 지켜라.

1. **한 문단 총평**
2. **100점 채점표와 점수 근거**
3. **가장 잘된 점 5개**
4. **Critical/Major/Minor 문제 목록**
5. **12개 설계 법칙별 판정표**
6. **인접 분야 전이 타당성 판정표**
7. **빠진 핵심 문헌·관점**
   - 우선순위
   - 문헌 또는 주제
   - 왜 필요한지
   - 문서의 어느 절에 들어가야 하는지
8. **중복되거나 줄일 수 있는 부분**
9. **우선 수정 계획**
   - P0: 사실 오류·출처 오류·현재성 문제
   - P1: 논지와 근거를 강화하는 수정
   - P2: 가독성·구조·서지 형식 개선
10. **최종 판정**
    - `그대로 공유 가능`
    - `경미한 수정 후 공유 가능`
    - `주요 수정 후 공유 가능`
    - `핵심 사실 검증부터 다시 필요`
