## 1. 결론

만들 대상은 여러 AI에게 자유롭게 회의시키는 프로그램이 아니다.

> **사용자의 목표를 작업 계약으로 바꾸고, 필요한 AI 세션만 실행하며, 일반 코드가 상태·권한·검증·재시도·종료를 통제하는 로컬 실행 제어기**다.

가장 중요한 결정은 다음과 같다.

1. 범용 오케스트레이터와 실제 프로젝트는 서로 독립된 저장소다. 범용 저장소 아래에 프로젝트들을 넣지 않는다.
2. 범용 원본의 얇은 실험판을 별도 기준 과제로 검증한 뒤 실제 프로젝트를 외부 pilot으로 검증하고, 그 결과를 반영한 release candidate를 프로젝트가 채택한다.
3. 프로젝트는 범용 코어의 버전을 고정하고 프로젝트 전용 설정·지식·검증기·훅을 가진다. 전체 코드를 복사하는 fork는 기본이 아니라 탈출구다.
4. 고정된 `P1·P2·P3·V1·R1` 조직은 없앤다. 세션은 작업에 필요할 때 생성되는 단기 실행 인스턴스다.
5. AI 세션끼리 직접 대화하지 않는다. 작업 계약, 주소가 있는 산출물, 구조화된 결과를 오케스트레이터가 중계한다.
6. AI의 “완료했습니다”는 후보 결과일 뿐이다. 자동검사와 필요한 검토를 통과해야 작업이 완료된다.
7. 읽기 중심의 독립 작업만 기본 병렬화한다. 공유 작업장의 쓰기는 기본적으로 한 번에 하나다.
8. 전체 계획을 한 번에 믿지 않는다. 짧은 구간을 실행하고 관찰한 결과로 다음 작업을 연다.
9. 실행 상태의 정본은 Desktop 화면이나 AI 대화가 아니라 로컬 원장이다.
10. 오케스트레이터가 단일 Codex 직접 사용보다 낫다는 비교 결과가 나오기 전에는 성공했다고 부르지 않는다.

## 2. 목표와 비목표

### 2.1 목표

- 사용자가 여러 세션에 프롬프트와 결과를 복사하는 일을 줄인다.
- 긴 프로젝트를 중단 후 재개할 수 있게 한다.
- 독립 작업은 안전하게 병렬 실행한다.
- AI가 아닌 코드가 권한, 상태 전이, 예산, 완료 조건을 집행한다.
- 작업자에게 필요한 정보만 제공해 컨텍스트 오염을 줄인다.
- 잘못된 쓰기, 낡은 입력, 중복 실행, 실패한 검증을 탐지한다.
- 프로젝트마다 다른 지식·도구·검증 규칙을 코어와 분리한다.
- 실행 흔적을 비교 실험과 회귀 테스트에 사용할 수 있게 남긴다.
- Codex가 바뀌거나 다른 세션 실행기로 교체돼도 범용 상태 모델을 유지한다.
- 최초 구현과 검증 범위는 Git으로 관리되는 프로젝트로 한정하고, 비 Git 작업장은 실제 요구가 생긴 뒤 adapter로 확장한다.

### 2.2 비목표

- 에이전트 수를 최대화하는 것
- 사람처럼 보이는 회사 조직이나 영구 AI 직원을 만드는 것
- 모든 프로젝트를 하나의 중앙 플랫폼에 등록하고 관리하는 것
- 처음부터 완전한 자율 작업 분해와 동적 조직 재편을 구현하는 것
- LLM 검토자를 절대적인 품질 게이트로 두는 것
- 일반 프로그램이 해결할 수 있는 상태·해시·테스트 계산을 AI 조정 세션에 반복시키는 것
- Codex가 이미 제공하는 세션 생성, 샌드박스, 서브에이전트, 앱 관리형 worktree UI를 동일한 형태로 재구현하는 것
- schema v1 또는 구현되지 않은 schema v2를 그대로 범용화하는 것

## 3. 근거와 설계 판단의 강도

### 3.1 근거 구분

| 구분 | 이 설계에서의 사용법 |
|---|---|
| 검증 문헌 | 여러 분야에서 반복되는 상태·계약·폐루프·권한·검증 원칙의 근거 |
| v1 코드와 실행 로그 | 실제로 발생한 통신 경합, 직렬 꼬리, 상태 비대화, 비용 문제의 경험 근거 |

| Claude 아키텍처 심사 | fork 유지보수, Codex 기능 중복, 초기 계층 수에 대한 독립 검토 |
| 현재 Codex 공식 문서 | 세션·샌드박스·서브에이전트·worktree 등 현재 제품 경계 확인 |
| 이 문서의 새 결정 | 위 근거를 종합한 설계 가설. 구현 후 비교 실험 필요 |

### 3.2 경험에서 직접 확인된 문제

`이어서 작업`의 v1은 실제로 구현·실행됐다. 확인된 대표 결과는 다음과 같다.

- 0-3 최초 P 병렬 구간은 작업자 시간 합계 39.28분에 비해 임계경로가 16.15분이었다. 다만 동일 작업의 실제 단일 세션 기준선은 없으므로 전체 성능 향상으로 확대할 수 없다.
- 0-3 전체는 통신기 수정과 복구를 포함해 198.8분, 9개 배치가 걸렸다.
- Brain은 0-3에서 31회, 0-4에서 15회 실행됐다.
- 0-3에서 계산 가능한 Brain 사용량은 918.17크레딧 이상, 0-4에서는 283.99크레딧 이상이었다.
- SDK 실행 중 Desktop 조회를 겹치자 세션이 중단된 사건이 있었고, 두 경로를 겹치지 않게 한 재시험은 성공했다.
- worker 완료 신호가 실제 terminal event보다 먼저 도착한 경합과 수분 단위 finalize 지연이 관측됐다.
- 0-4 상태 파일은 55,194개 입력 지문을 포함해 약 82.1MB로 커졌다.
- V1은 실행됐지만 어떤 결함을 얼마나 더 발견했는지 비교 자료가 없었다.
- 단일 세션과의 동일 조건 비교, EU4 외 프로젝트 적용, schema v2 구현·시험은 없었다.

따라서 v1은 “멀티 세션 자동 중계가 가능하다”는 것은 보여줬지만 “전체적으로 더 효율적이고 범용적이다”는 것은 증명하지 못했다.

### 3.3 문헌에서 가져온 원칙

- 결정론적 상태와 확률적 판단의 경계를 나눈다.
- 에이전트 수가 아니라 작업의 독립성과 결합도를 보고 병렬화한다.
- 대화보다 작업·산출물·증거·승인 상태를 먼저 설계한다.
- 전체 계획을 고정하지 않고 관찰 후 재계획하는 폐루프를 사용한다.
- 공유 컨텍스트를 최소화하고 큰 근거는 주소로 전달한다.
- 생성기와 다른 실패 모드를 가진 검증 수단을 사용한다.
- 실패, 재시도, 취소, 보상, 사람 이관을 정상 흐름으로 모델링한다.
- 품질뿐 아니라 비용, 지연, 사람 개입, 복구성, 안전을 함께 측정한다.

관련 근거는 [폭넓은 문헌조사](../research/ai-orchestration-broad-literature-review.md) §5·§6·§9·§13·§14와 [실용 사례 및 방법론](../research/ai-orchestration-practical-cases-and-methods.md) §7·§9·§10에 정리돼 있다.

## 4. 배포와 계보 구조

### 4.1 저장소 관계

```text
[범용 원본 저장소]
local-agent-orchestrator
  ├─ 범용 상태·정책·스케줄링 코어
  ├─ 세션 실행기 인터페이스
  ├─ Codex 어댑터
  ├─ 프로젝트 팩 템플릿
  └─ 범용 기준 과제와 안전 시험
             │
             │ release v0.1 / v1.0
             ▼
[실제 프로젝트 저장소 A]       [실제 프로젝트 저장소 B]
EU4-handbook                  web-service
  └─ .orchestrator/             └─ .orchestrator/
     core_version: v1.0            core_version: v1.1
     프로젝트 규칙                 프로젝트 규칙
     지식·프롬프트                  지식·프롬프트
     검사·훅                       검사·훅
```

프로젝트 A와 B는 범용 원본 저장소의 하위 폴더가 아니다. 서로 독립된 저장소이며 서로의 실행 상태를 공유하지 않는다.

### 4.2 “복사 후 프로젝트에 맞게 재구성”하는 방법

사용자가 원한 계보는 유지하되, 범용 코어 전체를 매번 복사해 생기는 fork drift는 줄인다.

1. 범용 원본의 검증된 버전을 태그한다.
2. 실제 프로젝트에 프로젝트 팩 `.orchestrator/`를 생성한다.
3. 프로젝트 팩은 채택한 코어 버전과 원본 출처를 기록한다.
4. 프로젝트 고유 변경은 설정, 지식, 검사, 훅에서 수행한다.
5. 여러 프로젝트에 공통인 결함만 범용 원본으로 되돌린다.
6. 프로젝트가 원할 때만 코어 버전을 올리고 자기 회귀시험을 다시 돌린다.

### 4.3 전체 fork가 허용되는 경우

아래 조건을 모두 만족할 때만 코어 전체 fork를 사용한다.

- 프로젝트가 코어의 상태 모델이나 실행 의미를 바꿔야 한다.
- 설정이나 훅으로 표현할 수 없다는 실제 사례가 있다.
- upstream 업데이트를 수동 병합할 비용을 받아들인다.
- `derived_from`, 원본 remote, 기준 tag, 로컬 변경 목록을 기록한다.

전체 fork는 정상 적용 방식이 아니라 **확장 경계가 실제로 부족할 때 쓰는 탈출구**다.

## 5. 전체 구조

```text
사용자
  │ 목표·제약·승인
  ▼
┌─────────────────────────────────────────┐
│ 결정론적 Control Plane                  │
│ 요청 접수 → 계약 검사 → 상태 원장       │
│ ready 계산 → 세션 배정 → 예산·권한 집행 │
│ 결과 수집 → 검증 게이트 → 재시도·종료   │
└───────────────┬─────────────────────────┘
                │ 구조화된 작업 계약
                ▼
┌─────────────────────────────────────────┐
│ Agent Plane                             │
│ Worker / Reviewer(조건부)               │
│ 계획·통합은 필요할 때 수행하는 작업     │
└───────────────┬─────────────────────────┘
                │ 결과 계약·산출물 주소
                ▼
┌─────────────────────────────────────────┐
│ Verification & Workspace Plane          │
│ 테스트·린트·스키마·diff·정책 검사       │
│ shared workspace / Git worktree adapter │
└───────────────┬─────────────────────────┘
                ▼
       원장·이벤트·산출물·측정값
```

### 5.1 결정론적 Control Plane

일반 코드가 담당한다.

- Run·Task·Attempt·Session 상태 전이
- 작업 의존성과 실행 가능 상태 계산
- 동시 실행 슬롯과 자원 잠금
- 읽기·쓰기·외부 행동 권한 검사
- 입력 지문과 stale 판정
- 결과 스키마 검사
- 테스트·린트·정책 명령 실행
- 재시도 횟수, 시간, 사용량 한도
- terminal 확인, 중복 결과 방지
- 중단 후 상태 조정과 재개
- 사람 승인이 필요한 지점에서 정지

### 5.2 Agent Plane

AI가 담당한다.

- 사용자 요청의 의미 해석
- 모호한 조건과 가정 발견
- 작업 분해안 제안
- 코드·문서·분석 결과 생성
- 자동검사로 판정할 수 없는 의미 충돌 판단
- 고위험 결과의 독립적 검토
- 여러 후보의 의미적 통합

AI는 상태 행을 직접 수정하거나 자기 결과를 최종 승인하지 않는다.

### 5.3 Project Pack

프로젝트에만 속하는 내용이다.

- 작업장 위치와 프로젝트 식별자
- 허용 읽기·쓰기 경로
- 프로젝트별 명령과 검증기
- 작업 유형과 능력 프로필
- AGENTS.md 등 프로젝트 지식의 주소
- 위험 등급과 승인 정책
- 외부 시스템 어댑터
- 프로젝트 전용 프롬프트와 결과 형식
- 프로젝트 전용 회귀 과제

### 5.4 Runtime Adapter

세션 제품과 코어 사이의 교체 가능한 경계다.

최소 인터페이스 개념은 다음과 같다.

```text
start_session(task_envelope, runtime_profile) -> session_handle
resume_session(session_handle, feedback)      -> turn_handle
observe(turn_handle)                          -> runtime_status
collect(turn_handle)                          -> result_envelope
interrupt(turn_handle)                        -> interrupt_result  # 지원할 때만
capabilities()                                -> runtime_capabilities
usage(turn_handle)                            -> measured_usage | unknown
```

`runtime_capabilities`에는 최소한 `supports_interrupt`, `supports_usage`, `supports_resume`를 둔다. 코어는 지원 여부를 확인하기 전에 선택 기능을 호출하지 않는다. Codex 어댑터는 공식 SDK·App Server·현재 앱 기능 중 검증된 경로만 사용한다. Desktop UI 상태는 원장의 정본이 아니다.

## 6. 핵심 데이터 모델

핵심 실행 계층은 네 개만 둔다.

```text
Run
 └─ Task
     └─ Attempt
         └─ Session
```

초기 코어에서 `Artifact`, `Check`, `Decision`, `Event`는 계층을 늘리는 부모가 아니라 이 네 개에 연결되는 기록이다. 정식 `Requirement` 엔티티는 두지 않고 Run의 필드와 버전으로 표현한다.

### 6.1 Run

사용자 목표 한 건의 실행 단위다.

- 원문 요청
- 원문 요청의 출처와 수신 시각
- 완료 조건
- 제약과 금지선
- 요구사항 버전
- 실행에 사용한 인증 방식(`auth_method`)
- 현재 상태
- 전체 시간·세션·재시도 예산
- 사용한 프로젝트 팩과 코어 버전
- 최종 결정과 미해결 항목

### 6.2 Task

독립적으로 할당하고 결과를 검증할 수 있는 작업 단위다.

- 목적과 완료 조건
- 선행 Task
- 입력 Artifact
- 읽기·쓰기 범위
- 필요한 능력 프로필
- workspace mode
- 검증 계획
- 위험과 승인 필요 여부
- 병렬 가능성

Task가 너무 작아 세션 시작 비용보다 작으면 합친다. 완료 조건을 독립적으로 쓸 수 없으면 아직 Task가 아니다.

### 6.3 Attempt

Task의 한 번의 실행 시도다.

- 사용한 Task 계약과 입력 지문
- 시도 번호와 시작 원인
- 배정한 Session
- 실제 결과와 산출물
- 실패 종류
- 검증 결과
- 재시도·교체·차단 결정

재시도는 기존 Attempt를 덮어쓰지 않고 새 Attempt를 만든다.

### 6.4 Session

Codex thread 같은 실제 AI 실행 인스턴스다.

- runtime 종류와 runtime별 식별자
- 모델·추론 설정을 가리키는 profile
- 작업 디렉터리와 샌드박스
- 시작·종료·interrupt 상태
- 마지막 확인 시각
- 사용량과 terminal 근거

Session ID는 프로젝트 Git에 고정하지 않는다. 다른 PC에서는 새 로컬 Session이 만들어질 수 있다.

### 6.5 요구사항 기록

초기 구현은 별도 `Requirement` 테이블과 freeze·amendment 상태 기계를 만들지 않는다. Run에 원문 요청, 출처, 완료 조건, 가정, 미확정 항목, `requirements_version`을 저장하고 Task와 Check가 해당 버전을 참조한다.

- 의미·범위·완료 조건이 바뀌면 Run의 요구사항 버전을 올린다.
- 기존 Task의 유효성을 다시 판정하고 무효화된 Task는 `SUPERSEDED`로 보존한다.
- 작은 작업은 완료 조건 체크리스트만 사용한다.
- 요구 변경으로 완료된 Task를 반복해서 무효화하는 사례가 누적될 때만 정식 Requirement 엔티티를 승격한다.

### 6.6 Artifact

세션과 단계 사이에 전달되는 주소 가능한 산출물이다.

- 파일·패치·보고서·테스트 출력의 위치
- 작성 Attempt
- 형식과 크기
- SHA-256
- 민감도와 보존 정책
- 다른 Artifact에서 파생된 관계

큰 원문과 대화 로그를 상태 DB에 넣지 않는다.

### 6.7 Check와 Decision

`Check`는 기계 검증 결과, `Decision`은 승인·차단·예외 판단 기록이다.

- Check: 명령, 범위, exit code, 결과 Artifact, 적용한 요구사항
- Decision: 결정 주체, 근거, 대상 상태, 승인 범위, 시각

AI reviewer의 의견은 Decision의 근거가 될 수 있지만 단독으로 상태를 통과시키지 않는다.

### 6.8 Team을 별도 핵심 계층으로 두지 않는 이유

팀은 프로젝트에 따라 유용할 수 있지만 초기 범용 상태의 필수 부모는 아니다.

- `frontend`, `research`, `security` 같은 팀 이름만으로 실제 능력이 생기지 않는다.
- 능력 차이는 데이터, 도구, 권한, 모델, 검증 기준, 출력 계약으로 표현해야 한다.
- Task에 `group` 또는 `capability_profile`을 붙이면 팀별 보기와 배정은 가능하다.
- 실제로 팀 단위 예산·팀장·공유 기억이 반복적으로 필요해질 때만 Team 엔티티를 승격한다.

즉, 세션 여러 개를 특정 팀처럼 묶는 것은 지원하되 **팀은 먼저 화면과 정책상의 그룹으로 시작하고, 영구 AI 조직으로 만들지 않는다.**

## 7. 세션 구조

### 7.1 세션 종류

| 종류 | 생성 조건 | 기본 권한 | 종료 원칙 |
|---|---|---|---|
| Worker | 실행 가능한 Task가 생겼을 때 | Task별 최소 권한 | Task Attempt가 끝나면 종료 |
| Reviewer | 자동검사로 판정 못 하는 위험·의미 항목이 있을 때 | 읽기 전용 | 독립 의견을 반환하면 종료 |

계획·재계획·의미적 통합이 필요하면 그것도 목적과 완료 조건이 있는 Task로 만들고 해당 능력 프로필의 Worker가 수행한다. `Coordinator`와 `Integrator`는 초기의 고정 세션 종류가 아니다. 같은 기능이 반복되고 독립된 수명·권한·예산이 필요하다는 실행 증거가 생길 때만 별도 유형으로 승격한다.

진행표를 갱신하기 위한 R1 같은 AI 세션은 범용 코어에 두지 않는다. 실행 보고서는 결정론적 exporter가 원장에서 생성한다.

### 7.2 세션 수명

- 기본은 Task Attempt 단위의 짧은 세션이다.
- 같은 Attempt의 명확한 오류 수정은 같은 세션을 한 번 재개할 수 있다.
- 컨텍스트 오염, 도구 경합, terminal 불확실, 요구 변경이 있으면 새 세션으로 교체한다.
- 역할 이름과 thread ID를 영구 결합하지 않는다.
- 계획·통합 판단을 맡은 Worker도 heartbeat나 상태 조회 때문에 깨우지 않는다.
- 세션이 끝나도 Run과 Task 상태는 원장에 남아 재개된다.

### 7.3 기본 통신 토폴로지

```text
                사용자
                  │
          승인·요구 변경
                  ▼
          결정론적 오케스트레이터
          /          │           \
     Worker A     Worker B      Reviewer
          \          │           /
           └──── Artifact/Result ┘
                  │
        자동검사·통합·상태 전이
```

- worker끼리 직접 메시지를 보내지 않는다.
- reviewer는 worker의 대화 전체가 아니라 요구사항, diff, 산출물, 검사 결과를 받는다.
- 계획·통합 판단 Task에는 모든 로그를 넣지 않고 상태 요약과 필요한 근거 주소만 준다.
- 같은 모델을 여러 번 부르는 것만으로 독립 검증이라 주장하지 않는다.

## 8. 전체 실행 프로세스

### 8.1 1단계: 요청 접수

1. 사용자 원문을 변경하지 않고 저장한다.
2. 목표, 완료 조건, 금지선, 승인 필요 행동을 분리한다.
3. 확인할 수 없는 조건은 가정으로 표시한다.
4. 위험이 낮고 단순하면 별도 계획 AI 없이 사람이 준 작업을 그대로 사용한다.
5. 모호하거나 긴 작업이면 계획 능력 프로필의 Worker가 별도 Task에서 계획안을 제안한다.

### 8.2 2단계: 실행 계약 확정

각 Task에 다음을 선언한다.

```yaml
id: T2
goal: "요청 제한 기능 구현"
depends_on: [T1]
inputs: ["artifact:T1-structure-summary"]
read_scope: ["src/**", "tests/**"]
write_scope: ["src/middleware/**", "tests/rate_limit/**"]
workspace_mode: shared_serial_write
capability_profile: code_change
checks: [lint, unit_test, write_scope]
review_policy: targeted
approval: none
```

이 예시는 데이터 모양을 설명하기 위한 것이며 확정 Schema가 아니다.

의미·범위·완료 조건을 바꾸는 수정은 Run의 새 요구사항 버전으로 기록하고, 필요한 경우 사용자 승인을 받는다. 단순 오탈자나 기계적 보강은 변경 이유만 남긴다.

### 8.3 3단계: 실행 가능 Task 선택

Task가 `READY`가 되려면 다음을 모두 만족해야 한다.

- 선행 Task가 검증까지 통과했다.
- 필요한 입력 Artifact가 존재하고 hash가 맞다.
- 실행 중인 Task와 금지된 자원 충돌이 없다.
- 세션·시간·사용량 예산이 남아 있다.
- 필요한 사용자 승인이 완료됐다.
- runtime과 workspace 준비 상태가 확인됐다.

### 8.4 4단계: 세션 배정과 실행

1. 능력 프로필에 맞는 runtime profile을 고른다.
2. 최소 샌드박스와 작업 디렉터리를 부여한다.
3. TaskEnvelope와 입력 Artifact 주소만 전달한다.
4. dispatch 전에 Attempt와 입력 지문을 원장에 기록한다.
5. runtime이 반환한 session/turn 식별자를 Attempt에 연결한다.
6. 진행 보고는 상태 변경이나 실제 blocker가 있을 때만 수집한다.

### 8.5 5단계: 결과 회수

세션은 최소 다음 결과 계약을 반환한다.

```text
status_claim
summary
artifacts
changed_paths
checks_run_by_worker
assumptions
warnings
requested_followup
```

`status_claim=completed`는 AI의 주장이다. 오케스트레이터는 terminal 상태와 Artifact 저장을 확인한 뒤 `REPORTED`로만 이동한다.

### 8.6 6단계: 검증

검증 순서는 고정한다.

1. 결과 스키마와 필수 Artifact
2. 허용 경로 밖 변경
3. 입력 stale 여부
4. 프로젝트별 lint·test·schema·수치 검사
5. 실제 외부 상태 또는 실행 효과
6. 자동검사로 판정할 수 없는 항목의 조건부 reviewer
7. 통합 후 전체 검사

생성자가 실행한 테스트는 증거로 보존하지만, 가능하면 오케스트레이터가 같은 명령을 독립적으로 다시 실행한다.

### 8.7 7단계: 실패와 재시도

실패를 다음처럼 구분한다.

| 실패 종류 | 기본 처리 |
|---|---|
| 일시적 runtime 오류 | 예산 안에서 재시도 |
| 명확한 구현·형식 오류 | 실패 근거를 주고 같은 세션 한 번 재개 |
| timeout·interrupt 미지원 | Attempt를 실패 처리하고 Session을 격리한 뒤 늦게 온 결과를 폐기 |
| stale input | 결과를 채택하지 않고 새 입력으로 새 Attempt |
| 권한·쓰기 범위 위반 | 즉시 차단, 변경 격리, 사용자 보고 |
| terminal 불확실 | Session 격리 후 runtime reconcile |
| 요구사항 모호성 | 사용자 또는 별도 의미 판단 Task 대기 |
| 반복 무진척 | 재시도 중단, blocked |
| 외부 부작용 부분 성공 | 영수증 확인 후 보상 또는 사람 이관 |

재시도 횟수는 설정값이고 무한 반복을 허용하지 않는다. `supports_interrupt=false`이거나 interrupt 확인에 실패하면 중단 성공을 가정하지 않는다. 해당 Session을 격리하고 이후 결과를 채택하지 않으며, 최소 권한 sandbox와 timeout으로 남은 영향을 제한한다. 사용량 정보가 없으면 0으로 기록하지 않고 `unknown`으로 기록한다.

### 8.8 8단계: 종료

기술적 완료 조건은 다음이다.

- 필수 Task가 모두 검증 통과
- 필수 Artifact 존재
- 미승인 외부 행동 없음
- 전체 통합 검사 통과
- 차단 상태와 미해결 요구 조건 없음

이 조건이 충족되면 Run을 완료한다. 보고서, 대시보드, Excel 갱신은 완료 후 파생 산출물이며 기술적 완료를 다시 열지 않는다. 보고서 생성 자체가 필수 결과인 프로젝트만 예외다.

## 9. 상태 모델

### 9.1 Run 상태

```text
DRAFT
  → READY
  → RUNNING
  → VERIFYING
  → COMPLETED

어느 단계에서든 조건에 따라:
WAITING_APPROVAL / BLOCKED / FAILED / CANCELLED
```

### 9.2 Task 상태

```text
PENDING → READY → RUNNING → REPORTED → VERIFYING → SUCCEEDED
                         └→ RETRYABLE_FAILED → READY
                         └→ BLOCKED
                         └→ FAILED
                         └→ CANCELLED
```

요구 변경으로 더 이상 유효하지 않은 Task는 `SUPERSEDED`로 보존하고 삭제하지 않는다.

### 9.3 상태 전이 원칙

이 절이 상태 전이의 단일 규범이다. 다른 절의 상태 관련 설명은 실행 절차를 요약한 것이며 충돌할 경우 이 절을 따른다.

- AI 응답은 직접 상태를 변경하지 않는다.
- 하나의 코드 경로만 상태 전이를 수행한다.
- 상태 전이와 대응 Event 기록은 같은 트랜잭션에서 처리한다.
- 동일 runtime 결과를 두 번 받아도 상태가 중복 전이되지 않아야 한다.
- 상태와 runtime 표시가 다르면 원장은 불일치 사실을 기록하고 재조정한다.
- 이미 일어난 외부 행동은 상태를 되감는 것으로 취소됐다고 간주하지 않는다.

## 10. 상태 저장과 실행 기록

### 10.1 정본

초기 범용 설계에서는 **SQLite 원장**을 정본으로 사용한다.

- Run·Task·Attempt·Session의 현재 상태 테이블이 현재 상태의 유일한 정본
- append-only Event 테이블은 감사·진단 기록이며 현재 상태의 대체 정본이 아님
- Check·Decision·Artifact 메타데이터
- 상태 전이와 Event append를 하나의 트랜잭션으로 기록

상태 테이블과 Event가 불일치하면 자동으로 어느 한쪽을 다른 쪽에서 재구축하지 않는다. Run을 차단하고 불일치 범위, 마지막 정상 트랜잭션, 적용할 복구 절차를 기록한 뒤 명시적으로 복구한다.

schema v2의 `events.jsonl → reducer → state.json`은 감사와 재생에 유리하지만, Windows의 cross-process append, seq, 손상 복구, reducer migration까지 한꺼번에 구현해야 한다. 로컬 1인용 초기 구조에는 SQLite 원장과 append-only Event 테이블이 더 단순한 출발점이다.

완전한 event sourcing은 다음 필요가 실측될 때 재검토한다.

- 현재 상태 테이블을 이벤트만으로 재구축해야 하는 복구 요구
- 여러 프로세스나 여러 머신의 동시 writer
- 과거 정책 버전으로 상태를 재생해야 하는 감사 요구

### 10.2 큰 데이터의 위치

DB에는 큰 원문·로그·파일 내용을 넣지 않는다.

```text
state root/
├─ ledger.sqlite
├─ runs/<run_id>/
│  ├─ request/
│  ├─ tasks/<task_id>/attempts/<n>/
│  │  ├─ input/
│  │  ├─ output/
│  │  ├─ checks/
│  │  └─ runtime/
│  └─ report/
└─ exports/
```

DB는 경로, hash, 크기, 작성 주체, 보존 등급만 가진다.

### 10.3 설정과 실행 상태의 위치 분리

```text
프로젝트 저장소/.orchestrator/        버전 관리 대상
  프로젝트 설정·지식 주소·검사·훅

사용자 로컬 state root/               버전 관리 금지
  DB·세션 ID·실행 로그·임시 산출물
```

로컬 state root는 `project_id`로 작업장과 연결한다. 다른 PC로 옮길 때는 세션 ID를 복사하지 않고, redaction된 Run 인수인계 bundle만 export/import한다.

### 10.4 Schema 버전과 migration

- 원장에는 현재 `schema_version`과 적용한 migration 이력을 기록한다.
- 코어는 지원하지 않는 미래 버전이나 불완전한 migration 상태에서 실행을 시작하지 않는다.
- migration은 적용 전 일관된 백업을 만들고, 실패하면 새 Run dispatch를 차단한다.
- Event 형식에도 버전을 두되 과거 Event를 현재 상태로 자동 재생하는 기능은 초기 범위가 아니다.

### 10.5 실행 잠금과 백업

- 한 state root에는 상태를 변경하는 controller를 한 번에 하나만 허용하는 배타 실행 락을 둔다.
- 두 번째 controller는 락 소유자와 마지막 확인 시각을 보고하고 쓰기를 시작하지 않는다.
- 백업은 `ledger.sqlite`만 복사하지 않고 해당 시점에 참조되는 Run Artifact와 함께 일관된 묶음으로 만든다.
- 복구 시험은 DB와 Artifact가 모두 존재하고 hash가 맞는지 확인한다.
- 오래된 락을 해제하는 절차는 실행 중인 controller가 없음을 확인한 뒤 사람 또는 명시적 복구 명령이 수행한다.

## 11. 병렬 실행과 작업 공간

### 11.1 기본 규칙

- 정보 의존이 있으면 직렬이다.
- 동일 원본을 중복 조사하는 작업은 합친다.
- 읽기-읽기만 겹치는 독립 작업은 병렬 가능하다.
- 공유 작업장에서는 쓰기 Task를 한 번에 하나만 실행한다.
- 외부 DB, API, 메일, 배포처럼 되돌리기 어려운 행동은 별도 승인과 단일 실행자를 둔다.
- idle worker에게 세션 수를 채우기 위한 작은 일을 만들어 주지 않는다.

### 11.2 격리 수준

| 모드 | 용도 | 병렬성 |
|---|---|---|
| `read_only` | 조사·분석·검토 | 독립 입력이면 병렬 |
| `shared_serial_write` | 일반 코드·문서 수정 | 쓰기 한 개만 |
| `isolated_worktree` | 코어의 Git adapter가 만든 격리 작업장에서 수행하는 실험적 병렬 수정 | 별도 채택 기준 통과 후만 |
| `staged_external` | DB·바이너리·외부 시스템 변경안 생성 | 후보만 병렬, 실제 적용은 단일 실행 |

### 11.3 worktree의 한계

Codex 공식 문서는 ChatGPT desktop app이 Git 저장소에서 관리형 worktree를 만들고 chat마다 분리된 checkout을 제공한다고 설명한다. 공식 SDK 문서에는 앱의 managed worktree 생성·Hand off를 호출하는 인터페이스가 없다. 따라서 SDK 기반 코어의 `isolated_worktree`는 앱 기능에 위임하지 않고 일반 Git worktree adapter가 직접 관리한다. managed worktree의 위치 설정 가능 여부처럼 제품 버전에 따라 달라질 수 있는 세부 기능에는 의존하지 않는다.

어느 방식의 worktree든 다음은 자동 해결되지 않는다.

- 두 branch의 의미 충돌
- 병합 후 통합 테스트
- Git에 없는 외부 원자료와 고정 TEMP
- 한 개만 실행 가능한 로컬 서버·게임·DB
- ignored secret의 복사와 노출 정책
- stale input 판정

따라서 worktree는 workspace adapter 하나이지 오케스트레이션 전체의 안전성 증명이 아니다.

### 11.4 복구 원칙

- 코드·문서 변경은 Git diff·commit·worktree를 우선 복구 수단으로 사용한다.
- 전체 작업장 hash snapshot을 상태 DB에 넣지 않는다.
- Task 입력과 변경 대상에 필요한 범위만 fingerprint한다.
- 소유권이 확실한 새 임시 파일만 자동 정리한다.
- 다른 세션이나 사용자의 변경일 가능성이 있으면 자동 복원하지 않고 차단한다.
- 외부 행동에는 멱등성 키, 영수증, 가능하면 보상 동작을 정의한다.

## 12. 검수와 사람 개입

### 12.1 검수 정책

| 조건 | 검수 방식 |
|---|---|
| 결과가 스키마·테스트·수치로 완전히 판정 가능하고 위험이 낮음 | 자동검사만 |
| 문서 의미, 설계 적합성, 일부 요구사항 해석이 필요함 | targeted reviewer |
| 보안·정책·외부 행동·넓은 변경·높은 불확실성 | 독립 full reviewer + 필요시 사용자 승인 |
| 자동검사 실패 또는 권한 위반 | reviewer에게 보내지 않고 먼저 차단·수정 |

### 12.2 요구사항 검수

schema v2의 V1-C 아이디어는 고정 역할로 두지 않는다.

- 작고 명확한 요청: 요구사항 체크리스트와 사용자 원문 대조를 코드가 수행
- 모호하거나 고위험인 요청: 별도 요구사항 reviewer를 조건부 실행
- 의미가 바뀌는 요구사항 버전 변경: 사용자 승인
- 단순 누락 보강: 변경 근거와 영향만 기록

### 12.3 결과 검수

- 작업 세션과 다른 새 세션을 사용한다.
- worker의 긴 대화 이력은 주지 않는다.
- 요구사항, diff, Artifact, 자동검사 결과, 미확정 항목만 제공한다.
- reviewer에게 수정 권한을 주지 않는다.
- reviewer의 의견과 자동검사가 충돌하면 코드가 자동으로 한쪽을 선택하지 않고 근거를 모아 별도 의미 판단 Task 또는 사용자에게 올린다.

### 12.4 사용자 승인이 필요한 기본 경우

- 사용자 요청의 의미·범위·완료 조건 변경
- 외부 발송, 결제, 배포, 삭제 같은 비가역 행동
- 허용 권한 확대
- 예산 상향
- 보호된 파일 또는 시스템 경로 접근
- 검증 기준 완화
- 소유권이 불명확한 복구

사람 개입은 실패가 아니라 정상적인 제어 상태다.

## 13. 예산과 모델 사용

### 13.1 고정 역할별 모델표를 코어에 넣지 않는다

코어는 `P1=Luna`, `V1=Terra` 같은 이름을 모른다. 프로젝트 또는 로컬 runtime profile이 다음 능력만 선언한다.

- 빠른 읽기·분류
- 깊은 계획·통합
- 코드 수정
- 독립 검토
- 사용 가능한 도구와 샌드박스
- 측정 가능한 사용량 종류

### 13.2 예산 축

- 최대 동시 세션 수
- 최대 총 세션·turn 수
- Task별 최대 Attempt
- Run과 Task wall-clock timeout
- 사용량·token·credit 한도: runtime이 실제 값을 제공할 때만
- 사람 승인 대기 시간
- 저장 공간과 보존 기간

사용량을 읽을 수 없으면 `unknown`으로 표시하고 세션 수·시간·재시도로 보수적으로 제한한다.

### 13.3 조정 비용을 줄이는 구조

- 상태 조회와 heartbeat는 일반 코드가 수행한다.
- 정상 결과의 hash·개수·exit code를 AI 조정 세션이 다시 계산하지 않는다.
- 계획·통합 능력의 Worker는 계획, 예외, 의미 충돌, 최종 통합이 실제로 필요할 때만 호출한다.
- 자동검사와 reviewer가 같은 정상 근거를 반복해 읽지 않게 입력을 분리한다.
- 진행 보고서는 AI가 아니라 원장에서 생성한다.

│     ├─ recover.py       reconcile·stale·백업·Git 작업장 복구

## 15. Codex와 범용 코어의 책임 경계

현재 공식 문서에서 확인되는 Codex 기능은 다음과 같다.

- SDK에서 로컬 thread 시작·계속 실행·ID 기반 재개
- Python SDK의 로컬 app-server JSON-RPC 제어
- turn별 `read_only`, `workspace_write`, `full_access` 샌드박스
- 서브에이전트 병렬 실행과 main thread로의 요약 반환
- 앱의 Git worktree 생성과 local handoff
- `AGENTS.md`의 root-to-cwd 지침 계층

따라서 범용 코어가 직접 만들어야 할 것은 Codex thread 자체가 아니다.

| Codex/runtime에 맡길 것 | 범용 오케스트레이터가 소유할 것 |
|---|---|
| thread 실행·resume, 지원되는 경우 interrupt·usage | Run·Task·Attempt 상태와 업무 의미 |
| 모델 추론과 도구 사용 | 어떤 Task를 언제 실행할지 |
| 샌드박스의 실제 집행 | Task별 최소 권한 정책 |
| subagent의 내부 실행 | 결과 계약, 독립성, 예산, 채택 여부 |
| 앱 UI에서의 managed worktree 생성·Hand off | SDK 실행용 Git worktree 생성·격리·병합·통합 검증 |
| AGENTS.md 로딩 | 어떤 지식을 어느 Task에 제공할지 |

공식 SDK 문서는 로컬 Codex agent의 프로그램 제어를 CI/CD, 자체 agent, 내부 도구·워크플로의 사용 사례로 안내한다. 인증 문서는 ChatGPT 계정 인증을 신뢰된 CI/CD에서 유지하는 경로도 문서화하지만, 같은 자리에서 **API key가 자동화의 기본 권장값**이라고 명시한다. 따라서 SDK 자동화 자체가 비지원이라고 단정하지 않는 동시에, 개인 ChatGPT 구독 로그인의 과금 미터와 다중 세션 한도도 API key와 같다고 가정하지 않는다.

구현 전 통제 실행으로 다음을 확인한다.

- Python/TypeScript SDK 실행이 어느 사용량 미터에 기록되는가
- 개인 구독에서 프로그램 실행과 다중 세션이 어떤 한도로 취급되는가
- 실행에 실제로 사용한 인증 방식은 무엇인가

마지막 값은 Run의 `auth_method`에 기록한다. 인증 방식이 불명확하면 비용 비교 실험을 시작하지 않는다.

## 16. 범용성 검증 계획

### 16.1 검증 순서

사용자가 원한 “범용 원본을 먼저 검증하고 프로젝트에 적용”하는 순서를 다음처럼 구체화한다.

```text
설계 동결
  → 인증·과금 가설 확인
  → 가짜 runtime으로 상태·실패 시뮬레이션
  → 실제 Codex 단일 세션 연결 시험
  → B0 기준선 기록과 B1 최소 실험판 비교
  → 별도 기준 저장소 A에서 코드 작업 시험
  → 별도 기준 저장소 B에서 조사·문서 작업 시험
  → 실제 프로젝트 1개를 외부 pilot/fixture로 시험
  → pilot에서 발견한 범용 결함만 코어에 반영
  → 실패·중단·권한·stale 시험
  → release candidate
  → 실제 프로젝트가 해당 버전을 채택
```

기준 저장소 A와 B는 범용 원본 아래의 실제 프로젝트가 아니라 독립된 시험 작업장이다. `C:\Users\SSAFY\Documents\이어서 작업`을 pilot으로 쓰더라도 범용 코어의 소유 저장소나 최초 맞춤 대상이 아니라 외부 fixture로만 취급한다. pilot의 프로젝트 고유 이름·역할·스키마를 코어에 편입하지 않으며, 코어 소스에서 `EU4`, `P1`~`P3`, `V1`, `R1`, `Brain` 같은 고유 문자열이 0건인지 회귀 검사한다.

### 16.2 비교 기준선

| 기준선 | 설명 |
|---|---|
| B0 | 사용자가 Codex 단일 세션을 직접 운영 |
| B1 | 오케스트레이터가 단일 worker를 순차 실행하고 자동검사 |
| B2 | 독립 읽기 작업을 복수 worker로 병렬 실행 |
| B3 | 위험 기반 reviewer까지 조건부 실행 |

총 시간이나 정확도 하나만 비교하지 않는다.

### 16.3 시험 유형

1. 엄격한 순차 의존 코드 작업
2. 서로 독립된 조사·분석 작업
3. 자동검사만으로 판정 가능한 수정
4. 의미 검토가 필요한 문서·설계 작업
5. 모호하거나 불가능해 `BLOCKED`가 정답인 작업
6. 실행 중 controller 강제 종료 후 재개
7. worker terminal 불확실과 중복 결과 전달
8. 허용 경로 밖 쓰기 시도
9. 실행 중 입력 변경에 따른 stale 판정
10. 외부 부작용을 흉내 낸 멱등성·보상 시험

### 16.4 측정 지표

공통 지표:

- 최종 성공률과 반복 성공률
- 사용자가 발견한 누락·오류
- wall-clock p50·p95
- 세션·turn·재시도 수
- 사용량이 제공되는 경우 성공 1건당 token·credit
- 사람 개입·승인·수동 복사 횟수
- 오케스트레이터 자체 준비·통합·검수 시간
- 자동검사가 잡은 오류와 통과 후 유출된 오류
- 중단 후 재개 성공률
- stale·권한·중복 실행 차단률
- 상태와 실제 외부 결과를 설명하는 데 걸린 시간
- 코어의 누적 개발·디버깅 시간
- 실험 1회당 필요한 코어 수정 횟수와 변경량

자동판정 가능한 코드·구조화 작업은 사람 중계 횟수, 수동 복사, 복구 개입, 자동검사 후 유출 오류를 중심으로 본다. 의미 판단이 필요한 문서·설계 작업은 사람 판단 자체를 실패로 세지 않고, 판단에 필요한 근거를 모으는 시간, 미해결 조건을 드러내는 비율, 최종 판단까지 걸린 시간을 별도로 측정한다.

### 16.5 범용 원본의 채택 조건

고정 숫자를 문헌의 법칙처럼 선언하지 않는다. 첫 실험 전에 다음 상대 조건을 등록하고 결과에 따라 보정한다.

- 자동판정 가능 계열에서 B1이 B0보다 성공률을 떨어뜨리지 않으면서 사람 중계·복구 부담을 줄일 것
- 의미 판단 계열에서 B1이 B0보다 성공률을 떨어뜨리지 않으면서 판단 근거 수집과 미해결 조건 식별 시간을 줄일 것
- B2가 B1보다 독립 작업의 벽시계 시간을 줄이고 통합·재작업 비용이 그 이득을 먹지 않을 것
- B3 reviewer가 추가 비용에 비해 실제 결함을 발견할 것
- 중단·중복·권한 위반·stale 시험에서 조용한 잘못된 완료가 없을 것
- 코드 작업과 조사·문서 작업 두 계열에서 독립 기준 저장소 1개와 실제 프로젝트 외부 pilot 1개가 코어 변경 없이 프로젝트 팩만 바꿔 실행될 것
- 코어 소스의 프로젝트 고유 문자열 회귀 검사가 0건일 것

이 조건을 못 맞추면 에이전트 수를 늘리지 않고 구조를 줄인다. B1조차 B0보다 낫지 않다면 필요한 것은 오케스트레이터가 아니라 좋은 프로젝트 지침과 검증 스크립트일 수 있다.

### 16.6 구현 확대 게이트

전체 아키텍처를 한 번에 구현하지 않는다.

```text
가설 1: ChatGPT 로그인 SDK 실행의 지원·한도·과금 경계 확인
  → 통과하면 B1 최소 실험판만 구현
  → 가설 7: 사전에 고정한 작업 표본으로 B0와 B1 비교
  → 통과하면 B2·B3와 이후 단계로 확장
```

가설 7은 B1 코드 없이는 검증할 수 없으므로 “가설 1과 7 통과 전 구현 금지”라고 표현하지 않는다. 가설 1은 B1 코드 착수의 게이트이며, 사용자가 감당할 수 있는 비용 안에서 공식적으로 문서화된 인증 경로를 쓸 수 있을 때만 통과한다. 가설 7은 전체 구조 확대의 게이트다. 가설 7의 표본과 사람 개입 횟수·개입 시간·wall-clock·복구 시간·측정 가능한 사용량 또는 API 비용은 실험 전에 고정한다. 2주는 운영상 timebox 제안일 뿐 성공 기준이 아니며, 시간이 부족하다고 표본을 사후 축소하지 않는다.

## 20. 최종 설계 판정

이 범용 오케스트레이터의 중심은 “여러 AI를 부리는 중앙 AI 관리자”가 아니다.

```text
범용 코어가 소유하는 것
  상태 / 계약 / 의존성 / 권한 / 예산 / 검증 / 복구 / 기록

AI 세션이 소유하는 것
  의미 해석 / 후보 생성 / 코드·문서 작업 / 예외 판단 / 제한된 검토

프로젝트가 소유하는 것
  지식 / 경로 / 도구 / 검사 / 위험 / 승인 / 전용 확장
```

이 분리를 유지하면 범용 원본을 먼저 검증한 뒤, 서로 독립된 실제 프로젝트가 자기 전용 오케스트레이터 구성을 가져갈 수 있다. 반대로 고정 팀, 영구 세션, EU4 전용 경로, 전체 검수, Excel 기록, Desktop 우회책을 코어에 넣으면 schema v1의 특화와 비용 문제를 다시 만들게 된다.

첫 구현의 성패는 기능 수가 아니라 다음 한 문장으로 판정한다.

> **단일 Codex 세션을 사람이 직접 운영하는 것보다, 더 적은 사람 중계와 복구 부담으로 같은 수준 이상의 결과를 반복해서 만드는가?**

이 설계는 심사 지적을 반영해 동결됐다. 인증·과금 가설 1을 통과한 뒤 B1 최소 실험판만 구현하며, 가설 7을 통과하기 전에는 병렬 worker·조건부 reviewer·worktree를 포함한 전체 아키텍처로 확장하지 않는다.
