## 1. 한 문단 최종 총평

이 설계는 이전 심사의 지적을 형식적으로 받아넘긴 것이 아니라 실제로 소화했고, 특히 v1에서 **관측된 사실**(0-3의 198.8분, 82.1MB 상태 파일, Desktop/SDK 경합, 신호 선행 도착)과 v2의 **미구현 가설**을 끝까지 분리해서 서술한 점은 이런 종류의 설계 문서에서 드물게 정직하다. 핵심 판단 — 결정론적 control plane이 상태·권한·검증을 소유하고 AI는 의미 해석과 생성만 맡는다, 세션은 Task Attempt 단위 단기 인스턴스다, 완료는 AI의 주장이 아니라 검사 통과다, 읽기만 먼저 병렬화한다 — 은 문헌과 Codex 공식 문서가 양쪽에서 지지하며 유지해야 한다. 그러나 두 가지가 프로젝트 성립 자체를 좌우한 채 미결로 남아 있다. 첫째, 구독 인증으로 프로그램 자동화를 돌린다는 비용 전제는 §19 질문 1로 인식은 됐지만 **"어느 미터에 기록되는가"만 물었을 뿐 "그 사용 방식이 권장·지원되는가"를 묻지 않았고**, 공식 인증 문서는 프로그램 워크플로에 API key를 권장한다고 두 번 명시한다. 둘째, §16.1은 여전히 기준 저장소 두 개로 범용성을 검증하고 release candidate를 낸 뒤 실제 프로젝트가 채택하는 순서인데, 정작 §19 질문 10은 그 순서로 범용성을 주장할 수 있는지 스스로 의심한다 — **문서가 자기 계획을 자기가 못 믿는 상태**다. 여기에 사실 오류가 하나 있다. §15는 worktree 생성·handoff를 Codex에 위임할 항목으로 표에 넣었지만 공식 문서상 그것은 **Codex 앱의 UI 기능**이고 SDK 경로에서 쓸 수 있다는 근거가 없다. 이 세 가지를 고치면 설계 문서 자체는 동결 가능한 수준이며, 구조를 다시 짤 필요는 없다.

## 2. 내가 이해한 현재 상황과 설계 목표

### 2.1 사실 (문서와 공식 자료에서 확인)

- 설계자는 EU4 핸드북 프로젝트용 schema v1 세션 컨트롤러를 **실제로 구현·운영했다**. Brain 1 + 고정 worker P1·P2·P3 + reviewer V1 + 기록 R1의 6 thread 구조다.
- v1 0-3 구간에서 작업자 실행시간 합계 39.28분 대 병렬 임계경로 16.15분이 관측됐다. **동일 작업의 단일 세션 기준선은 없다.**
- 0-3 전체는 통신기 수정과 복구를 포함해 198.8분, 9개 배치가 걸렸다.
- Brain은 0-3에서 31회, 0-4에서 15회 실행됐고 계산 가능한 사용량은 각각 918.17크레딧 이상, 283.99크레딧 이상이었다.
- SDK 실행 중 Desktop 조회를 겹치자 세션이 중단됐고, 겹치지 않게 한 재시험은 성공했다.
- worker 완료 신호가 실제 terminal event보다 먼저 도착한 경합과 수분 단위 finalize 지연이 있었다.
- 0-4 상태 파일은 55,194개 입력 지문 때문에 약 82.1MB가 됐다.
- V1의 실행과 PASS는 기록됐으나 **어떤 결함을 추가로 발견했는지 비교 자료가 없다.**
- schema v2는 기획만 됐고 구현·시험되지 않았다.
- EU4 외 프로젝트 실행 기록은 없다.
- 현재 설계 문서는 구현·단위시험·라이브시험 0건이다.

### 2.2 설계 가설 (근거는 있으나 아직 실증되지 않은 것)

- 일반 코드가 상태·권한·예산·검증·복구를 쥐면 v1의 Brain 비용과 상태 비대화가 줄어든다.
- Task Attempt 단위 단기 세션이 고정 thread 장기 재사용보다 컨텍스트 오염이 적다.
- 위험 기반 조건부 검수가 전량 V1 검수보다 비용 대비 효과가 좋다.
- 버전 고정 코어 + `.orchestrator/` 프로젝트 팩이 전체 fork보다 유지보수가 싸면서 프로젝트 독립성을 지킨다.
- SQLite 원장 + append-only Event가 완전 event sourcing보다 1인 로컬에 적합하다.
- 읽기 병렬만 먼저 열면 v1의 병렬 쓰기 위험을 피하면서 이득의 상당 부분을 얻는다.

이 여섯 가지는 전부 **아직 검증되지 않았다.** 문서가 이 점을 §3.1 표와 §20에서 명시한 것은 적절하다.

### 2.3 미확인 전제 (프로젝트 성립에 영향)

1. **SDK로 프로그램에서 세션을 돌릴 때 ChatGPT 구독 사용량이 적용되는지, 그리고 그 사용 방식이 권장되는지** — §19 질문 1. 아래 P0-1.
2. 기준 저장소 두 개로 범용성을 주장할 수 있는지 — §19 질문 10. 아래 P0-2.
3. SDK에서 `interrupt`와 사용량 회수가 가능한지 — §5.4 인터페이스가 전제하고 있다.
4. SDK thread와 Desktop task의 상태·수명이 일치하는지 — v1에서 경합이 관측된 지점이다.
5. subagent와 별도 SDK thread가 같은 것인지 다른 것인지.

## 3. 설계의 가장 강한 논리 5개

**3.1 v1의 관측 사실과 v2의 미구현 가설을 끝까지 분리했다**

§3.1 근거 구분표와 §3.2가 "v1은 멀티 세션 자동 중계가 가능하다는 것은 보여줬지만 전체적으로 더 효율적이라는 것은 증명하지 못했다"고 스스로 결론 내린 부분이 이 문서에서 가장 신뢰가 가는 대목이다. 자기가 만든 것의 성과를 과장하지 않았다. 0-3의 39.28분 대 16.15분을 인용하면서 곧바로 "동일 작업의 단일 세션 기준선이 없으므로 확대할 수 없다"고 제한한 것은, 문헌조사 §14.6이 요구하는 예산 통제 원칙을 자기 데이터에 적용한 것이다.

**3.2 완료를 AI 주장이 아니라 검사 통과로 정의하고 그 경계를 상태로 못 박았다**

§8.5의 `status_claim=completed` → `REPORTED`, §9.2의 `RUNNING → REPORTED → VERIFYING → SUCCEEDED`는 이 시스템이 존재해야 할 이유 그 자체다. 문헌조사 §9.5의 `Catching One in Five`(LLM 심판이 체계적 문제 9개 중 2개만 포착, 운영 게이트는 100라운드 중 0건 표시)와 §9.2의 운영 조사가 직접 지지한다. `REPORTED`라는 중간 상태를 이름까지 붙여 만든 것은 구현자가 오해할 여지를 줄인다.

**3.3 R1을 AI에서 결정론적 exporter로 바꿨다**

§7.1의 "진행표를 갱신하기 위한 R1 같은 AI 세션은 범용 코어에 두지 않는다"와 §13.3의 "진행 보고서는 AI가 아니라 원장에서 생성한다"는 v1 비용 문제에 대한 정확한 대응이다. 원장에 있는 사실을 AI에게 다시 읽혀서 표로 만들게 하는 것은 순수한 낭비였고, 그 낭비가 Brain 크레딧으로 측정됐다. 이건 관측된 문제에 대한 관측 기반 해결이다.

**3.4 Team을 엔티티로 승격하지 않은 판단**

§6.8의 논증 — "팀 이름만으로 실제 능력이 생기지 않는다, 능력 차이는 데이터·도구·권한·모델·검증 기준·출력 계약으로 표현해야 한다, Task에 `group`/`capability_profile`을 붙이면 팀별 보기와 배정은 가능하다" — 은 문헌조사 §15 오해 1과 정확히 일치하며, 내 이전 심사의 [중간-7] 지적을 형식이 아니라 논리로 수용했다. 승격 조건("팀 단위 예산·팀장·공유 기억이 반복적으로 필요해질 때")까지 적어둔 것이 좋다.

**3.5 v1에서 실제로 아팠던 지점만 골라 채택 목록에 넣었다**

§18.1의 채택 목록(R-R 허용과 W-W·W-R·R-W 제한, 입력·쓰기 범위 명시 계약, terminal 확인 전 완료 금지, input fingerprint와 stale 분리, Attempt 단위 재작업, 상태 정본을 UI와 분리)은 전부 v1에서 사고가 났던 자리다. 특히 "상태 정본을 UI와 분리"는 Desktop 조회가 SDK 실행을 중단시킨 사건에 대한 직접 대응이다. 예방적 우려가 아니라 경험에서 온 항목만 남긴 것이 §18.3 보류 목록의 길이로도 확인된다.

## 4. 맥락 이해 심사 결과

설계자의 제약을 최대한 인정하고 평가한다.

**결론: 이 제약 아래에서 합리적이다. 다만 검증 순서와 초기 범위에 무리가 있다.**

- **1인, 종량 비용 부담, 실제 프로젝트에 쓸 도구가 필요함** — 이 세 제약 아래에서 "코드가 상태를 쥐고 AI는 생성만" 구조는 옳은 선택이다. 대안(모든 것을 AI에게 맡기는 자율 조직)은 v1에서 이미 비용으로 실패했고, 반대 극단(자동화 없이 사람이 다 중계)은 v1을 만든 이유 자체를 부정한다.
- **v1을 만들어본 경험이 있다는 것은 이 설계의 실질적 자산이다.** 문서가 인용하는 실패는 전부 남이 겪은 것이 아니라 자기가 겪은 것이고, 그래서 §18.1 채택 목록에 추상적 항목이 거의 없다.
- **단계 A~F(§17)의 의존 순서는 타당하다.** 특히 "가짜 runtime으로 상태·실패 시뮬레이션"을 실제 Codex 연결보다 앞에 둔 것은, 상태 머신 버그와 runtime 버그를 섞지 않겠다는 뜻이며 1인 디버깅 비용을 크게 줄인다.
- **다만 §16.1의 검증 순서는 이 제약 아래에서 오히려 비싸다.** 1인이 기준 저장소 A·B를 만들고 유지하는 비용은 실제 프로젝트 하나를 병행하는 비용과 비슷하거나 더 크다. 그런데 기준 저장소에서 얻는 정보는 실제 프로젝트에서 얻는 정보보다 적다.
- **§6.5 Requirement와 §12.2 요구사항 검수는 이 제약에서 과하다.** 요구사항 freeze와 amendment 승인은 요청자와 구현자가 다른 팀의 장치다. 1인이 자기 요청을 스스로 승인하는 절차가 되고, 절차가 형식화되면 지켜지지 않는다.

**맥락 이해 심사의 판정**: 구조는 유지, 초기 범위는 축소, 검증 순서는 실제 프로젝트를 포함하도록 수정.

## 5. 맥락 비의존 심사 결과

v1·v2의 역사와 매몰비용을 근거로 인정하지 않고, 오늘 처음 같은 요구를 받았다고 가정한다.

**결론: 상당 부분 같은 결론에 도달하지만, 세 가지는 오늘이라면 넣지 않는다.**

같은 결론에 도달하는 것:
- 결정론적 control plane과 AI plane의 분리
- Run → Task → Attempt → Session 4계층
- SQLite 원장 + append-only Event (완전 event sourcing 보류)
- 완료 = 검사 통과, AI 주장은 `REPORTED`
- 읽기 병렬 우선, 공유 작업장 쓰기 직렬
- 버전 고정 코어 + 프로젝트 팩
- Team 비엔티티화

오늘 처음이라면 **넣지 않을 것**:

1. **Requirement 엔티티와 freeze/amendment (§6.5, §8.2, §12.2)** — 요구사항 추적은 Run의 완료 조건 목록과 정수 버전으로 충분하다. 별도 엔티티, 원자화, amendment 승인 절차는 사례가 하나(EU4 핸드북의 요구사항 표류)뿐인 개념이다. 그 하나의 사례는 "요구사항이 흔들려서 고생했다"는 경험이고, 그에 대한 최소 대응은 "완료 조건을 텍스트로 고정하고 바뀌면 버전을 올린다"이지 전용 엔티티가 아니다.

2. **Integrator 세션 (§7.1)** — 네 가지 세션 종류 중 유일하게 v1 경험에도 문헌에도 근거가 없다. "여러 산출물의 의미적 통합"은 Coordinator가 하거나, 애초에 Task를 그렇게 쪼개지 말았어야 하는 신호다. 제한된 쓰기 권한을 가진 다섯 번째 역할을 코어 표에 넣는 것은 §18.3에서 보류한 "Team leader 세션"과 같은 종류의 결정이다.

3. **Coordinator를 코어의 세션 종류로 고정하는 것 (§7.1)** — 초기에는 사람이 Task를 쓰는 것이 더 빠르고 정확하다. §8.1 4번이 "위험이 낮고 단순하면 별도 계획 AI 없이 사람이 준 작업을 그대로 사용한다"고 이미 조건부로 열어뒀는데, 오늘 처음이라면 **그 조건부를 기본값으로 하고 Coordinator를 §17 단계 F로 미룬다.**

**두 심사의 차이와 그 이유**

맥락 이해 심사는 Requirement·Integrator·Coordinator를 "v1에서 아팠던 자리에 대한 이해할 만한 대응"으로 본다. 맥락 비의존 심사는 같은 것을 "사례 하나에서 일반화한 조기 추상화"로 본다.

**이 차이는 억지로 합칠 필요가 없다.** 두 심사가 일치하는 것은 "이 세 가지가 없어도 나머지 설계는 온전히 성립한다"는 점이다. 그러므로 삭제가 아니라 **§18.3 보류 목록으로 이동**이 두 심사를 모두 만족한다. v1의 통증은 기록으로 남기고, 승격 조건은 §6.8이 Team에 대해 한 것과 같은 형식으로 적으면 된다.

## 9. 다섯 대안 비교표

작업 유형에 따라 결론이 다르므로 **코드 작업**과 **조사·문서 작업**을 나눠 표시한다.

| 기준 | ① 단일 세션 + AGENTS.md | ② Codex subagent/worktree + 검증 스크립트 | ③ 얇은 runner + SQLite + 자동검사 | ④ 현재 설계 전체 | ⑤ Temporal/Prefect/LangGraph |
|---|---|---|---|---|---|
| 사용자 중계 감소 | 낮음 | 중간 (사람이 지시해야 스폰) | **높음** | 높음 | 높음 |
| 구현·유지보수 비용 | **없음** | 매우 낮음 | 낮음 (1~2주) | **높음** (수개월, 1인) | 중간 (학습곡선 + Codex 어댑터는 직접) |
| 중단 후 재개 | 없음 (수동) | 없음 | **있음** (원장) | 있음 | **있음** (Temporal의 핵심 강점) |
| 상태·근거 추적 | 대화 로그뿐 | 대화 + 커밋 | **원장 + Artifact** | 원장 + Event + Check + Decision | 워크플로 이력 |
| 병렬 실행 이득 | 없음 | **있음** (읽기 중심 권장) | 읽기 병렬 | 읽기 병렬 → 단계적 확대 | 있음 |
| 쓰기 안전성 | 사람이 책임 | worktree (앱 전용) | 직렬 쓰기 | 직렬 → worktree adapter | 프레임워크가 보장 안 함 |
| 프로젝트별 독립성 | **완전** | **완전** | 높음 | 높음 (core 버전 고정) | 중간 (프레임워크 종속) |
| Codex 변경 내성 | **높음** | 낮음 (기능 의존) | 중간 (adapter 경계) | 중간 (adapter 경계) | 중간 |
| 구독/API 비용 전제 | 구독 그대로 | 구독 그대로 | **P0-1에 걸림** | **P0-1에 걸림** | **P0-1에 걸림** |
| 1인 운영 가능성 | **확실** | 높음 | **높음** | 중간 | 낮음 (운영 부담) |

**작업 유형별 결론**

- **조사·분석(읽기 중심)**: ②가 비용 대비 가장 유리하다. Codex subagent가 이미 병렬 스폰과 요약 반환을 제공하고, 충돌 위험이 없다. ③·④의 추가 가치는 "중단 후 재개"와 "근거 보존"뿐인데, 조사 작업은 재실행이 싸다.
- **코드 수정(쓰기 중심)**: ③이 최적점이다. 검증 게이트와 원장이 실질 가치를 만들고, 병렬 이득은 어차피 작다(문헌조사 §9.1의 순차 의존 −70%).
- **긴 다단계 작업(중단·재개가 잦음)**: ③ 또는 ④. 여기서만 ④의 추가 복잡성이 값을 한다.
- **⑤**: 이 요구에는 맞지 않는다. Temporal·Prefect는 durable execution을 제공하지만 Codex 세션 어댑터·sandbox 정책·검증 게이트는 어차피 직접 만들어야 하고, 1인 로컬 도구에 서버형 워크플로 엔진의 운영 부담을 더한다. 다만 **§17 단계 B의 "중단 후 재개"를 직접 구현하기 전에 Temporal의 durable execution 모델을 읽어보는 것**은 권한다 — 구현하지 않더라도 상태 설계의 참고가 된다.

**현재 설계(④)가 ③보다 나은 지점은 검증되지 않았다.** ④가 ③에 더한 것은 Requirement, Coordinator, Integrator, 위험 기반 3단 검수, Event 테이블이며 — 이 중 P1·P2에서 보류를 권고한 것을 빼면 ④는 ③에 수렴한다.

## 10. Clean-room 권고 아키텍처

과거를 계승할 의무가 없다고 가정했을 때, **현재 설계와 방향은 같고 크기가 약 30% 작다.**

### 10.1 같은 것 (그대로 채택)

- 결정론적 control plane / AI plane 분리
- Run → Task → Attempt → Session 4계층
- SQLite 원장 정본, Artifact는 파일시스템, DB에는 경로·hash·크기만
- 완료 = 검사 통과. AI 주장은 `REPORTED`
- 세션 간 직접 통신 금지, 계약·산출물·요약만 중계
- 읽기 병렬 우선, 공유 작업장 쓰기 직렬
- core 버전 고정 + `.orchestrator/` 프로젝트 팩, 전체 fork는 탈출구
- Team 비엔티티화
- Runtime adapter 경계
- 결정론적 report exporter

### 10.2 다른 것

**삭제하거나 보류할 것**

| 대상 | 처리 | 이유 |
|---|---|---|
| Requirement 엔티티 | Run 필드로 축소 | 사례 1건 (P1-7) |
| Coordinator | 단계 F로 | 초기엔 사람이 Task를 쓰는 게 빠르다 |
| Integrator | 보류 | 근거 없음 |
| freeze/amendment 절차 | 버전 정수 + Event | 1인이 자기를 승인하는 절차 |
| Decision 엔티티 | Event의 한 종류로 | 별도 테이블이 필요한 시점이 아직 아니다 |

**Codex에 위임할 것** — 8절 경계표대로. 단 worktree는 위임 불가(P1-3).

**직접 만들 것 (이것만)**

```
1. ledger        Run/Task/Attempt/Session/Check/Artifact/Event, 상태 전이 단일 경로
2. contract      TaskEnvelope 입력 계약 + 결과 계약 검증
3. runtime       Codex SDK 어댑터 (capabilities로 미지원 기능 우회)
4. verify        subprocess 검증 게이트 (경로 검사 + 프로젝트 명령)
5. schedule      의존성 + ready + 쓰기 직렬 슬롯
6. recover       중단 후 재개, stale 판정, 중복 결과 무시
7. cli           run / status / resume / cancel / report
```

7개 모듈. `benchmarks/`와 `templates/project-pack/`은 현재 설계 그대로 유지한다.

### 10.3 프로젝트 독립성 요구를 어떻게 지키는가

현재 설계와 동일하다. `.orchestrator/` 팩 + core 버전 고정 + 별도 저장소. clean-room 설계가 줄인 것은 **코어의 개념 수**이지 배포 구조가 아니다. 사용자의 "검증된 범용 원본을 프로젝트가 가져간다"는 요구는 그대로 지켜진다.

### 10.4 왜 삭제한 것들이 나중에 필요해질 수 있는가

이 판단이 틀릴 수 있는 경우를 적어둔다. Coordinator는 Task가 20개를 넘는 Run이 반복되면 필요해진다. Requirement 엔티티는 완료된 Task를 요구 변경으로 무효화하는 일이 잦으면 필요해진다. Integrator는 독립 조사 결과를 합치는 작업이 매 Run마다 나오면 필요해진다. **셋 다 승격 조건을 §18.3에 적어두고 관측하면 되며, 지금 만들지 않는 비용은 나중에 만드는 것뿐이다. 반대로 지금 만들면 검증 없이 코어 계약에 들어간다.**

## 13. 최종 판정

### `경미한 수정 후 설계 동결` — 단, 구현 착수는 가설 1·7 통과를 조건으로 한다

**설계 문서 자체**는 12절의 12개 항목을 반영하면 동결 가능하다. 구조를 다시 짤 필요가 없고, 4계층 데이터 모델·상태 머신·control plane 분리·프로젝트 팩 배포는 그대로 두어도 된다. 이전 심사에서 지적한 fork drift, Codex 기능 중복, 계층 과다는 실질적으로 반영됐다.

**그러나 이 판정을 "구현을 시작해도 좋다"로 읽으면 안 된다.** 두 개의 게이트가 남아 있다.

- **가설 1(비용 전제)이 실패하면** 이 설계는 문서로서는 온전해도 실행할 수 없다. 병렬 실험과 예산 설계를 다시 써야 한다. 코드를 쓰기 전에 반나절로 확인할 수 있는 것을 수개월 뒤에 알게 되는 것이 이 프로젝트의 가장 큰 위험이다.
- **가설 7(B1 > B0)이 2주 안에 실패하면** §16.5가 스스로 적어둔 대로 "필요한 것은 오케스트레이터가 아니라 좋은 프로젝트 지침과 검증 스크립트"일 수 있다. 이 문장을 문서에 적어둔 것은 설계자의 정직함이고, 실제로 그 결과가 나왔을 때 그 문장을 지키는 것이 더 중요하다.

마지막으로 한 가지. 이 문서에서 가장 값어치 있는 문장은 §20의 마지막 판정 기준이다.

> 단일 Codex 세션을 사람이 직접 운영하는 것보다, 더 적은 사람 중계와 복구 부담으로 같은 수준 이상의 결과를 반복해서 만드는가?

**이 기준을 구현 도중에 완화하지 않는 것이 이 프로젝트의 성패를 가른다.** v1에서 "멀티 세션 자동 중계가 가능하다"는 것을 보여줬을 때 그것을 성공으로 부르지 않은 판단이 이 설계를 여기까지 오게 했다. 같은 엄격함을 v2에도 적용하면 된다.
